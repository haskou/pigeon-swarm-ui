# Opaque mailboxes (client)

Client side of haskou/pigeon-swarm-node#289. Module: `src/contexts/mailboxes/`.

## Scope

- 1:1 channel at epoch 0 only.
- The only delivery path for direct 1:1 messages: sent, edited, deleted, reactions, pins, and read receipts. See Direct messages below.
- Direct inboxes can be replicated on up to three availability servers (haskou/pigeon-swarm-node#290). See Availability servers below.
- Contact presence inboxes, one per direct conversation side. See Contact presence below.
- No rotation announcement and no realtime hint.

## Key schedule

HKDF-SHA256 (`@noble/hashes/hkdf.js`, no salt, 32-byte outputs) over a shared 32-byte secret.

- `info` = label ‖ recipient UTF-8 ‖ u32be(epoch).
- Labels: `pigeon/mailbox/id/v1` (mailbox id), `pigeon/mailbox/post/v1` (post token), `pigeon/mailbox/envelope/v1` (envelope key).
- Read token: derived from the identity root key. See Read token below.
- Node-side capability hashes: SHA-256 hex of the token string (`BearerCapability.hash` from `@haskou/pigeon-swarm-crypto`; tokens must match `^[A-Za-z0-9_-]{20,128}$`).

Pinned vector: secret `0x01 × 32`, recipient `identity-bob`, epoch 0. The vector asserts the derived mailbox id, post token, and envelope key.

## Read token

- `MailboxReadToken.derive(rootKey, mailboxId)`: HKDF-SHA256 (no salt, 32 bytes) over the device-sealed root (`sessionRootKey(session)`). Info = `pigeon/mailbox/read/v1` ‖ mailbox id. Output is base64url.
- Pinned vector: root key `0x09 × 32`, mailbox id `mailbox-fixture-id`, token `MCkFZKBU05ZYpDeepqRuly-xXmS0bx7Hgq_m0ydOqPI`.
- The token is the same on every device that holds the root key, and it survives re-authorization. A device that lost its storage reads and acknowledges the same inbox without a new PUT. New inboxes persist only the cursor.
- The root key never reaches the node. Pairing seals it to the enrolling device's transport key (`DevicePairingCompletion`).
- The peer holds the conversation secret, which yields the mailbox id, post token, and envelope key, but not the root key. It cannot derive the token, so it cannot read, acknowledge, or delete the inbox.
- The root key also decrypts the identity keychain, which holds the conversation keys. Compromising it already exposes the messages, so the read token adds only the ability to read, acknowledge, or delete the inbox.
- Who can use it: holders of the identity root key, i.e. this identity's own devices. The 1:1 peer holds only the conversation secret, so it cannot read, acknowledge, or delete the inbox.
- What the node sees: create sends only `BearerCapability.hash(token)`. Each read and acknowledge sends the raw token as `Authorization: Bearer`, and the node checks it against that hash. The node therefore learns the raw token on every read and ack. It can already read and delete the inbox's ciphertext envelopes, and the token adds no new capability beyond that.
- Groups: do not reuse this derivation with a shared conversation or group secret as the input. Every holder of that secret could then read, acknowledge, and delete each member's inbox. Group inboxes need a per-member token. The group key schedule below derives it from the inbox owner's root key.

### Reader set

- Device reader: `MailboxReadToken.deriveDevice(rootKey, mailboxId, deviceCredential)`, same HKDF with info = `pigeon/mailbox/device-read/v1` ‖ u32be(len(mailboxId)) ‖ mailboxId ‖ credential UTF-8. Pinned vector: root key `0x09 × 32`, mailbox `mailbox-fixture-id`, credential `-----BEGIN PUBLIC KEY-----`, `AAAA`, `-----END PUBLIC KEY-----` joined by LF, gives `js4BVkg1uGoEfwYGrPmaTvGh7s8MuZnZhSg1zaYJzDA`.
- A device reads and acknowledges with its device reader. The same token rules as the root apply: the node sees the raw device token on each read and ack.
- The root reader lists, enrols, and removes readers, and it mirrors each acknowledgement, so the root cursor tracks the latest device ack.
- A device enrols its reader when it creates the inbox, and bridges it under the root reader when the inbox already exists (409). After a revoke, the revoking device first registers the new root reader through the replaced root (`previousDeviceSealedRootKey`), best effort. Recovery enrols it again after a re-creation. A refused bridge reads nothing (`reopenInbox` returns outcome `failed` with the sealed readers), and the bridge retries on the next pass.
- Pairing: before it returns the completion, the authorizer enrols the new device's reader, derived from the kept sealed root and the paired credential (`DevicePairingAuthorization.credential`), in the inbox of every direct conversation on the connected node and each picked availability server (`DirectMessageMailbox.enrolDeviceReader`). The node starts a new reader at cursor 0, so it keeps every retained record until the new device acknowledges it, including records another device acknowledged before the new device first opened the inbox. The enrol is best effort and never blocks the pairing: an inbox that does not exist yet, a reader past the cap, or a failed call logs one count-only line, and that inbox is joined on the new device's first open. Records another device acknowledged before such a late join are not kept for the new device. Of that backlog, the new device keeps and shows only records dated at or after its history floor (see Pairing history export).
- Cap: the node's `maxReaders` (`MAILBOX_MAX_READERS`) defaults to 129 on nodes that include haskou/pigeon-swarm-node#437: the root reader plus one reader per device, up to 128 devices. A device enrol past the cap is refused (409) and logged with the fixed inbox-create debug line. Its read then gets 404, recovers, and fails again on enrol with 409. `addReader` maps that 409 to `MailboxReaderLimitError`, and the sync shows the reader-limit notice instead of the generic one. A reader whose device was removed still counts until pruned; the first pass of an app session prunes before the read, so that slot can free in the same pass.
- Pruning: once per app session per mailbox and root, on the first sync pass or the first recipient prewarm open (`openInboxes`), whichever comes first. A device lists the readers and removes any hash that is not the root reader, its own device reader, or a device reader of a credential in the identity's device list, all derived from the device-sealed root. The root reader is never removed. A failed pass logs a fixed debug line and retries on the next sync.
- Mixed versions: a client from before this change reads and acknowledges with the root token only. Its acks do not move the device readers, so envelopes stay until the device readers acknowledge. Update every device.

### Alternatives

- Random token, persisted (previous design): lost with local storage. The node keeps the old inbox, so reads return 404 and the recreate PUT returns 409 until the 14-day retention expires.
- Derived from the conversation secret: rejected. The peer could read, acknowledge, and delete.
- Derived per device (`deviceId`): rejected. The device id changes on re-authorization and on "forget this device", which reproduces the loss.
- Epoch bump on 409 with a fresh mailbox id: rejected. Senders derive from the constant epoch 0, and the rotation announcement is not implemented. Senders would keep appending to the abandoned inbox, so messages would be lost silently. This needs the announcement from the node design doc first.

### Residual risk

- Mixed versions and the reader cap: see Reader set.
- Forget is best effort on readers: forgetting a device removes its device reader through the root token. A failed removal is left to the reader prune that other devices run on sync. The only device of an identity keeps its reader, because its revocation is never sent.
- Revoke rotates the root for the remaining devices (see `device-sealed-secrets-client.md`, Rotation). The revoking device keeps the root it replaced on the in-memory session (`previousDeviceSealedRootKey`). The device dialog reports the revoke done only after the cut-off (`revokeOtherDevice`, then `DirectMessageMailbox.cutOffRevokedReaders` and `GroupConversationMailbox.cutOffRevokedReaders`, run together). In the inbox of every direct conversation, on the connected node and each picked server, and in every readable generation inbox of this identity's groups (see Group readers), the cut-off registers the new root reader through the replaced root, then prunes. The prune removes the replaced root's readers and the revoked device's reader, so the revoked device cannot read records written after that point (#311, #405). An inbox that the rotated root cannot reach fails the cut-off while the replaced root still reads it; an inbox neither root reaches has nothing to cut off. Every inbox is attempted, and a failure is shown (`profile.deviceRevokeCutOffError`) after the rotated session is already stored, so it is never lost. The first sync of each inbox retries the bridge and prune. After that the revoked device has no reader, because it cannot fetch the sealed root (401). Other devices bridge through the new root reader. Authorship tags derive from the sealed root, and keychain heads open only under it, so a revoked device cannot forge own-inbox tags or read the post-revoke keychain.
- Revoke residuals (#311):
  - Window: envelope keys derive from the conversation secret, which the revoked device keeps, and the node authorizes each read by the reader set only. Records written between the revoke and an inbox's cut-off stay readable by the revoked device. The dialog waits for the cut-off of every inbox before it reports the revoke done; after a failed cut-off the window lasts until the next sync of that inbox prunes it.
  - The replaced root is held in memory only on the revoking session. If that app session ends before an inbox is cut off, the inbox keeps the replaced root's readers until a device that opens the rotated root `<root>.<previous root>` (#376) bridges and prunes it on its next sync. A device that missed more than one rotation cannot bridge (see `device-sealed-secrets-client.md`, Multi-rotation residual).
  - Group inboxes: a generation inbox superseded past the drain window is neither bridged nor cut off. It holds only records written before the drain; after a rotation its deletion (`deleteDrained`) is refused for the new root, and the device marks it deleted locally, so the node expires it with its retention.
- Forget rotates the root in the forgetting device's own revocation (#310, node `haskou/pigeon-swarm-node#289`): the remaining devices receive a fresh root that carries the root it replaced (see `device-sealed-secrets-client.md`, Rotation, Forget). A remaining device opens it with the replaced root as `previousDeviceSealedRootKey`, so each inbox open registers the fresh root reader through the replaced root and prunes the replaced root's readers, as after a revoke. Until a remaining device opens an inbox, the old root's readers stay registered on it, and a forgotten device that still holds the old root keeps read access to that inbox. If the node did not store the hand-over, the first remaining device to unlock rotates instead (`rotateLaggingRoot`) and bridges from the lagging root; the window then lasts until that unlock.
- Silent readers: a registered reader that stops acknowledging holds every envelope above its cursor until the node's retention expires them (default 14 days). While it is silent the mailbox can fill, and appends return 409. Pruning removes only readers whose device is gone, so a silent device that is still listed keeps its backlog. A paired device is enrolled at pairing, so it holds the backlog from then on until it first opens and acknowledges, or is revoked and pruned. A record dated before the paired device's history floor is dropped but still acknowledged, so it never holds the backlog.

## Group mailbox key schedule

Step 2 of node `docs/design/group-mailboxes.md` (haskou/pigeon-swarm-ui#174). Module: `src/contexts/groupMailboxes/`. Every group conversation runs on it (see Group conversation cutover).

- `MailboxKeySchedule.groupInbox(gen_k, identityId)` of `@haskou/pigeon-swarm-crypto` derives the material of one member inbox `I(Y,k)`. The client holds `gen_k` as `GroupMailboxGenerationSecret` (`domain/value-objects/`, 32 bytes as unpadded canonical base64url; a rejected value is never echoed in the error) and hands it to the library as a `SymmetricKey`. The client derives no inbox key itself.
- The library derives a per-identity slot `s_Y` from `gen_k`, then the mailbox id, post token and envelope key from the slot; its `docs/mailbox-keys.md` names the KDF, labels and limits. Any member derives every slot of its generation from the roster; nobody outside the generation can link an inbox to an identity. A slot is per identity, not per device: all devices of `Y` read the same inbox.
- `envelopeKey` is the AES-256-GCM key of the outer per-copy AEAD of decision D5: random nonce per copy, AAD `mailboxId`. The envelope cipher (`MailboxEnvelopeCipher`, see Envelopes) runs on WebCrypto, with a fresh 12-byte IV per copy and a non-extractable key limited to encrypt and decrypt.
- Read tokens: each device of `Y` reads `I(Y,k)` with its own registered reader token (`MailboxReadTokens`, see Reader set). Members can derive every inbox id, post token and envelope key of the generation, but no member's read token.
- None of the outputs depends on an identity or a group id. A member removed before generation `k + 1` has no `gen_{k+1}`, so it cannot derive any inbox of that generation.
- Vectors: `@haskou/pigeon-swarm-crypto/vectors/mailbox-key-schedule.json` (`groupInbox`, `invalidGroupInbox`) pins the schedule in the library's own suite. The client's specs derive inbox keys only through the library.

### Generations from MLS

Each group conversation is one MLS group (`GroupMailboxMlsEngine`, `infrastructure/mls/`, on the `MlsGroup` wrapper of the communities context). A leaf is a device; membership is checked against the conversation roster.

- `gen_0` is the exporter of the epoch the creator starts: `MLS-Exporter("pigeon/group-mailbox/gen/v1", "", 32)`.
- `gen_{k+1}` is the same exporter of the epoch after any commit: an add, a removal, a roster change, or a self-update. Each device commits a self-update of its own leaf on a cadence (`mls-group-encryption.md`, Who commits), so a copy of its state that leaked stops reading the group once the update is in. A removed member never holds the epoch the next generation is exported from.
- Whether the generation is behind comes from state, not from the last commit: each generation stores the epoch it was exported in, with a digest of the leaves (position and signature key) of that epoch, and it advances whenever the group is past that epoch. A commit that changes no leaf, a GroupContext-only one, therefore advances it too.
- A commit, a self-update included, is delivered in the generation-`k` inboxes (`deliveryGeneration`): the remaining members learn `gen_{k+1}` only by processing it.
- `gen_k` never travels. Because every add advances the generation, a joiner exports `gen_k` itself from the epoch its welcome puts it in. The inviter hands it only `{welcome, k}` over the 1:1 mailbox; the welcome is HPKE-sealed to the joiner's key package, and the index `k` is public. A wrong `k` only mislabels the generation; `k` must be a non-negative safe integer. Each welcome opens once: a device that already holds the group, has no matching key package, or gets a welcome no newer than the epoch it was removed in gets `MlsRejectedError`. A removed device can be added again with a new key package; its old group and generations are replaced. The key package is deleted only after the generation log and the group are saved, so a failed save leaves the welcome openable.
- Commits are rejected unless MLS accepts them. A commit for an epoch this device already left is never reprocessed, but its sender data must still open under that retained epoch, so a commit forged elsewhere is rejected instead of ignored.
- `decrypt` returns the plaintext and the sender leaf `{identityId, deviceId}` that MLS authenticated. A sender whose leaf is not in the current tree is rejected, so once a removal is applied, even messages the removed member sent in an earlier epoch are not read. Results are cached per ciphertext (SHA-256), so a reread does not consume the ratchet twice and the sender reads its own messages.
- The generation log (`GroupMailboxGenerationLog`, IndexedDB `IndexedDbGroupMailboxGenerationStore`) keeps every generation with its epoch, sealed with the device root (see Local state sealing). A superseded generation stays readable for 6 h (`readableGenerations`). That is enough for copies a member sent before it processed the change. A member that stays offline longer still finds the commit, because it reads its current generation until the commit moves it on; only messages sent to the old generation by such a lagging member are lost. When a rival that outranks it (see Same-epoch rivals) replaces a commit this device applied (`replaced`), the log rewinds to that epoch and is recomputed.
- The log is written before the MLS state, and any failed operation drops the cached group. Loading a group reconciles the log with it: generations past the stored epoch belong to a commit whose group save failed, so nobody received it; they are dropped, and the log advances if the stored group is past the epoch of its current generation. A retried add or removal therefore exports the generation of the commit it actually returns. `generation` and `readableGenerations` reconcile first. A generation advances only past the epoch it already holds, so reapplying a commit after a crash is idempotent.
- A device removed before a restart restores as removed and cannot encrypt.
- Authorisation: each leaf credential carries the signatures of its identity key and of its device key over the leaf key, and every device must be on the conversation roster. Every commit, made or received, is judged by verified leaf owners only: a commit whose committer leaf credential does not verify through the device key to the identity it names is rejected, whatever it carries, as is one whose update path leaves the committer's leaf to another identity or device (see `docs/mls-group-encryption.md`). Every commit by this device's own identity, whatever it changes, is made or applied only when the committing device is in its verified device set (#441); a peer's device chains to its identity through its leaf credential only, because another identity's transitions are not readable (residual: a peer's revoked device that keeps the identity key commits as that identity until its leaf is removed). Every add or removal commit, made or received, is checked against the roster (`GroupMailboxRoster`): only the creator and the admins still on it add devices or remove members (every member when it names neither); a removal of someone still on the roster never targets the creator or the remover, and an admin only by the creator. A commit that only rotates the committer's own leaf needs no role. A local add or removal is kept as pending state (sealed like the group) and adopted only once its commit is queued in the outbox; if queuing fails, the device stays at its epoch, and after a crash it adopts the pending state when its own commit comes back.
- Same-epoch rivals: commits for one epoch from different devices compete, and every member keeps the same winner whatever order they arrive in. A rival the latest roster no longer allows loses and is rejected. The others rank by `GroupMailboxRoster.priorityOf`: a commit by the creator first, then one that removes another identity, then the rest; only equal ranks fall to the lowest commit id. The rank depends only on the commit and the conversation's creator, so every member ranks alike. The commit id is the lowercase hex SHA-256 of the commit's unpadded base64url text, which every member derives from the commit bytes alone, never from a node record or envelope id. The committer chooses those bytes and can grind a low id, which wins only among equal ranks: of two rivals the roster allows, one that removes the other's committer always ranks higher (only the creator removes an admin, and a member who is no manager changes only its own leaves), so a low id never wins back a member's removal, nor an admin an epoch the creator commits. Each commit has its own rank rather than a comparison with each rival, so any number of rivals converge; hence a removal also outranks a commit by someone it does not remove, and two commits by the creator fall to the id. A removal of the committer's own devices ranks with the rest, or a member about to be removed could match its removal and win on the id. Residuals (see `docs/mls-group-encryption.md`, Security): an admin that grinds a low id against another admin's removal, a revoked device racing the removal of its own leaf, and a member offline longer than its inbox keeps the winner.
- Limits: a member that has not yet processed a removal holds its messages while the roster no longer lists the removed member (see Removal gap under Group conversation cutover); one that read the roster before the removal can still encrypt in the old epoch.
- Local state sealing (#376): the MLS state (groups, key packages, plaintext cache), the generation log and the handled control letters (see Control replay) are `DeviceSealedEntryStore` rows, sealed with AES-256-GCM under keys derived by HKDF-SHA256 from the device-sealed root (`DeviceRootRowKeys`, labels `pigeon-group-mls`, `pigeon-group-generations` and `pigeon-group-control`; communities use `pigeon-mls-state`). A row is keyed by identity id, kind and an HMAC-SHA256 tag of kind and id; the AAD is `['entry', identityId, kind, tag]`, and the id is sealed with the value. A per-identity canary decides on first access: under the session's root the rows are used; under the replaced root (`previousDeviceSealedRootKey`, after a revoke) every row of the identity is re-sealed under the new root in one transaction that checks the canary is unchanged, so an interrupted re-seal leaves the old rows and is retried; under neither root the identity's rows are dropped. A root the store re-sealed away from is refused, so a stale session cannot drop newer rows. Values are decrypted when read; the MLS store keeps up to 2,048 decrypted entries in memory (LRU). Rows stored unsealed before #376 are dropped by the database upgrade (version 2), never read. See `mls-group-encryption.md`, Security properties and limits.
- Session after a revoke: each group member (`GroupConversationMember`) reads one current session, which every call moves forward (`follow`). The MLS store, generation log, handled letters, outbox, inbox sync, notification pump and direct link all read it per use, so a removal commit queued during the revoke reconcile is sealed under the new root and delivered without a re-login. `follow` ignores a session of the same authorization epoch with a lower authorization revision than the current one, and a session whose root a followed session replaced (`previousDeviceSealedRootKey`), so a call that started before the revoke cannot move the member back to a replaced root mid-reconcile. Every revoke raises the revision, so this holds after several revokes, including for a root the member never saw. The member keeps only the SHA-256 of each replaced root, never the root itself. Covered by `removes a revoked device while a call with the session the revoke replaced runs` and `ignores a session from before two revokes while it follows only the last one` in `GroupConversationMailbox.spec.ts`.

### Control records

`GroupMailboxControl` (`infrastructure/control/`) carries the membership traffic of D8.

- Wire format (`GroupMailboxControlRecord`): one JSON object `{kind:'group-mailbox-control', version:1, conversationId, type, ...}`, binary fields in unpadded canonical base64url, each at most 40 000 bytes. `type` is `key-package-request` (`requestId`, 22 base64url characters, `deviceCredential`, the device-credential PEM of the one device asked, when a device asks its own identity, and `genesis`, `{creatorIdentityId, networkId, nonce}`, when the sender knows the group's genesis), `key-package-response` (`requestId`, `keyPackage`), `welcome` (`welcome`, `index`, and `deviceCredential`, the device-credential PEM of the one device the welcome adds) or `commit` (`commit`). `decode` returns null for anything else, never throws, and rejects padded, standard or non-canonical base64, a `deviceCredential` that is not a device credential and a `genesis` that does not derive `conversationId`. No record carries `gen_k`.
- Add: the inviter checks every joiner is on the roster and asks each for a key package over the 1:1 mailbox they share (`GroupMailboxDirectLink`). Only the device and session that sent the request take the answer, once, and only from that peer for that conversation; any other device or session of the inviter's identity ignores it and leaves it pending (#509). The request is taken before the add awaits anything, so concurrent copies of one answer count once; an add that throws gives the request back, so the letter's retry counts. The key package's credential must name that peer; any other key package is rejected. It commits, appends the commit to `I(Y, deliveryGeneration)` of every existing member (its own inbox included), then sends `{welcome, k}` over the 1:1 mailbox once per added key package, to the identity it belongs to, naming its device in `deviceCredential`.
- Device add (#417): a leaf credential binds a device (see `docs/mls-group-encryption.md`), so each device of an identity holds its own leaf. The device that leads its identity's leaves (see Reconcile) asks each verified device without a leaf for a key package over its own identity's notification link, naming that device in `deviceCredential`; only that device answers, and the answer must carry that device's credential. A device only the node lists is never asked. It commits the add like any add and sends each added device its own welcome over its own identity's link; only the device a welcome names opens it, and any other device of that identity ignores it. An identity's own add needs no manager: a member may add and remove leaves of its own identity only, never another identity's. A device applies any commit of its own identity, on its own leaves or not, only when the committing device is in its verified device set (#441).
- Remove: the commit goes to `I(Y, deliveryGeneration)` of every member that held a leaf before it, the removed member included. The removed member processes it, ends its group and learns it left the roster (RFC 9420 §12.4.2); it already holds `gen_k`, so the copy tells it nothing it could not read before, and the UpdatePath is never encrypted to it, so it never learns `gen_{k+1}`. A removed member that is offline until the copy expires sees a group that stays quiet.
- Commits are appended with the inbox keys of `MailboxKeySchedule.groupInbox`. The envelope id is seeded from the SHA-256 of the commit, the recipient's inbox of the generation after the commit, and the inbox it goes to, so a resend is stored once. A member being removed still holds `gen_k` and can append to `I(Y,k)`. With an id it could predict, it could store junk first and the node would drop the real commit as a duplicate. It could also hash one copy of the commit it got to see and race the remaining copies. It never learns the next generation, so it cannot derive any of these ids. Each member creates its own `I(Y,k)` once it holds `gen_k`. Commits go through the group outbox (below): an append that fails, for example because that inbox does not exist yet, stays queued and is retried, and `add` or `remove` resolves after the first attempt. There is no abandon path for a commit that never lands (#380).

### Send and receive

`GroupMailboxOutbox` (`infrastructure/outbox/`) sends and `GroupMailboxInboxSync` (`infrastructure/inbox/`) receives.

- Message wire format: a `message` control record (`ciphertext`) carries one MLS application message. Its plaintext is the one-to-one record envelope (`DirectMessageMailboxRecord`), so the record types match one-to-one, except `read`, which a group drops.
- Outer layer: each copy is sealed separately by `MailboxChannel.send` with the recipient inbox's envelope key (D5). The node sees one opaque envelope per member inbox and no plaintext.
- Outbox: a record is persisted, sealed under the device-sealed root (`GroupMailboxOutboxStore` on `DeviceSealedRowStore`), before its first append. Each copy keeps its envelope id across retries, so a retry is stored once. A failed append (missing inbox, 409, 429, network) keeps the copy and backs off from 5 s to 5 min. Later records to the same recipient wait behind it in every generation, so each member gets one sender's records in order, and a commit held in `I(Y,k)` holds back the messages of the epoch it starts, queued for `I(Y,k+1)`. Records enqueued in the same millisecond keep their order. The queue resumes after a restart. A message still queued after 14 days is kept as failed (see Failed message); a commit still queued then is dropped.
- Outbox state: `items(conversationId)` lists the queued records oldest first, each `held` while its last pass found a removal pending or the group unconfirmed (see Confirmation), or it was never sealed, `retry` once an attempt left a copy undelivered, and `pending` otherwise, and each message kept as failed as `failed`. `GroupConversationMailbox.withOutboxState` stamps this identity's own group messages with it (`ChatMessage.deliveryStatus`); a delivered message has none. The bubble of a held message reads "Waiting to send", a retrying one "Retrying", and both stay dimmed like a pending one; a failed one reads "Failed" with a Retry button, as a one-to-one send that failed. Only messages show it; queued edits, deletions, reactions and pins do not.
- Failed message: a message the outbox gives up on keeps its body and the copies it had not appended, is never sent again on its own, holds back no later record and no typing notice, and survives a restart. Retry (`GroupConversationMailbox.retry`, from the bubble) queues it again as a fresh record, its 14 days counted anew: it is re-encrypted in the current epoch for its pending recipients still in the group, or, if it was never sealed, sealed for every current member, a member who joined since included. A retry while this identity is off the group's roster is refused (`ConversationParticipantNotFoundError`) and the message stays failed. A failed message stays until it is retried, its deletion is queued (see Deleted message), or the device forgets the identity (see Storage); a logout that keeps the device keeps it.
- Stale generation: a message whose generation was superseded before every copy landed is re-encrypted in the current epoch, only for its pending recipients that are still members. A member who joined since never gets it. A message that can no longer be encrypted, as after this identity's removal or once it outgrew the record limit, is kept as failed (see Failed message). Any other re-encryption failure (storage, for one) keeps the record and backs off like a failed append. A commit belongs to its generation and is never re-encrypted; it is dropped once its generation has drained.
- Lost epoch: a delivered message stays in the outbox, its body and the members its copies reached only, while a rival commit could still win the epoch of their generation (`GroupMailboxGenerationLog.RIVAL_EPOCHS`, 8, the states the group keeps to switch to a rival). The generation is told apart by a one-way fingerprint of its secret, since a rival commit for the same epoch exports another secret under the same index. A landing whose generation is no longer on this device's branch of the generation log (`GroupMailboxGenerationLog.branch`), as after a rival won and rewound the device past it, is stranded however old it is: no member reads its inboxes, so the landed copies are re-encrypted in the epoch that won and appended again, like a stale generation; a recipient that already read the message keeps one copy, by its record tag. Such a row is not listed in `items` and holds back nothing; a commit records no landing. A row queued by a build before this change, without fingerprint and landings, is upgraded on resume: a message is re-encrypted in the current epoch for its pending recipients, and a commit takes the fingerprint of the readable generation of its index, or is dropped once that one drained (`mls-group-encryption.md`, Who commits).
- Deleted message: once this identity queues the deletion of its own message, the outbox forgets that message's row, body included, whether it was delivered and kept for its landings, still queued, or kept as failed (`GroupMailboxOutbox.enqueueMessage`, `deletes`). It is never appended again, also when a rival commit wins the epoch of its copies, and a retry of it finds nothing; the deletion is delivered like any message. The forget runs after any pass in flight, so that pass cannot store the row again. Residual: a row the store fails to remove stays at rest until the next resume finds it, and is then sent like any queued row. Otherwise a delivered body stays sealed on the device until no rival can strand its copies or `EXPIRY_MS` (14 days), whichever is first.
- Receive: `sync` reads every readable generation, oldest first. Reading creates this identity's inbox `I(self,k)` when it is missing (`MailboxChannel` recovery). Commits go to `GroupMailboxControl`; after an applied commit the generations are listed again (at most 8 rounds). Pages are 50 envelopes and acknowledged after their records are stored. A rejected envelope is still acknowledged, so a forged one cannot stall the inbox. `decrypt` rejects only for what MLS refuses (the library's `InvalidMlsGroupError`, `InvalidMlsCredentialError` and `InvalidMlsExtensionError`); any other failure, as a plaintext the device could not store, leaves the page unacknowledged, so it is read again. An envelope that failed to open 5 times (`MAX_FAILURES`, counted per inbox in local storage) is dropped and acknowledged. History floor: a commit is applied whatever its date, and a message is still decrypted and its author checked, so the group state moves on. A message dated before this device's history floor (see Pairing history export) is then dropped before it is stored, shown, notified or counted as unread, and its page is acknowledged as usual.
- Future epochs: a message from an epoch this device has not reached is rejected, not kept. Every epoch change of a group conversation, a self-update included, starts a new generation, so a member's genuine message of the next epoch lands in the next generation's inbox, read after the commit, and the outbox holds it until that commit landed. A forged message claiming a later epoch is dropped without stalling what follows it. A self-update therefore loses no message of the epoch it ends nor of the one it starts (`GroupMailboxInboxSync.spec.ts`).
- Authorship: MLS authenticates the sender leaf, and a record is accepted only when its `authorId` is that sender. Every record id is a `CommitmentId.groupMessage` of `@haskou/pigeon-swarm-crypto` bound to its author (format in its `docs/commitment-ids.md`), checked with `CommitmentId.isGroupMessageOf`. A record whose id was not made for its MLS sender is rejected, so no member can take the id of another member's message first, or edit, delete or react under it. A message id already held by another author is rejected. An edit or a deletion is accepted only from the author of its target, whose id must be bound to that author too. The authors come from the history store (see Group history), looked up by keyed tag one record at a time and cached for the sync pass, so the check survives a restart without opening the whole conversation. Pins and reactions are not restricted to the author.
- Group history: `GroupMessageHistoryStore` keeps each stored record in IndexedDB (`pigeon-group-history` version 3, scoped by `scopeClientStorageKey`). Rows are sealed with AES-256-GCM under `DeviceRootRowCipher.derive(root, 'pigeon-group-history', identityId)`, with AAD `['record', identityId, conversationTag, recordTag]`, so a row moved to another identity, conversation or slot does not open. Conversation and record ids are stored only as HMAC-SHA256 tags, under a key derived by HKDF-SHA256 from the device-sealed root with info `pigeon-group-history:tag:v1:<identityId>`, a label of its own. A replayed record collapses on its record tag, so the store does not grow. A per-identity canary record (`DeviceSealedCanaryRecords`, the rules of `DeviceSealedRowStore`) settles the root once per root and store, in one transaction (`GroupMessageHistoryDatabase.settle`). Under the root the session replaced (`previousDeviceSealedRootKey`, after a device revoke) every row is re-sealed under the new root with its tags recomputed under it, each in place under its sequence so arrival order and unread counts hold, and each read marker moves to its conversation's new tag; a row or marker that does not open is dropped, and the log line gives only the re-sealed and dropped counts. The replaced root is then listed in the record (at most 16 roots, as in `DeviceSealedRowStore`), so a tab or store still on it is refused with `REPLACED_ROOT`, its rows kept, instead of wiping the re-sealed history; so is a root published at a generation the record's does not exceed. Every write (`insert`, `putRead`) first checks in its own transaction that the canary still opens under the writer's keys, so a tab that settled before another re-sealed stores nothing. Under any other root, as after a skipped rotation, the identity's rows and read markers are wiped. A canary stored before the record, a bare sealed canary, reads as a record that lists no replaced root, so no database upgrade is needed. A wipe or re-seal that dropped at least one row is remembered in memory and reported by `GroupConversationMailbox.checkHistoryDropped(session)` until `acknowledgeHistoryDropped(identityId)` (see Device storage); a deliberate `forget` is not reported, and a wipe that finds no row is not either. `load(session, conversationId, limit)` opens only the latest `limit` arrivals and pages older ones on demand; opened records stay in memory per identity and root, so a reload of a loaded page decrypts nothing again. An upgrade from version 1 drops every version 1 row: local group history from before it is gone, and there is no read path for the old rows.
- Group unread: the `reads` store keeps one read marker per identity and conversation tag (`GroupMessageReadMarker`), sealed like a row with AAD `['read', identityId, conversationTag]`. It holds the last row sequence it accounted, the ids of other members' messages since the last read on this device (at most 200, then only a count), and the creation time of the newest message, clamped to the time it was accounted. `append` accounts the records it just stored without opening any stored row; rows stored after the marker, as after a crash in between, are opened and accounted on the next call. A deletion withdraws its message from the count; own messages, edits, reactions and pins never count. `markRead` moves the marker to the last row, and writes nothing when it is already there. History stored before a conversation's first marker counts as read; its newest message time comes from opening at most 50 of those rows. `activity(session, conversationId)` returns `{latestMessageAt, unreadCount}`.
- Drain: a generation inbox of this identity that is superseded for longer than the 6 h drain window is no longer read; at the end of a sync it is deleted from the node (`PigeonMailboxClient.delete`), and a 404 counts as deleted. It is deleted only once every reader of it has acknowledged at least as far as this device's reader (`listReaders`), so a device never deletes what another device of the identity has not read yet. An inbox that is not settled is left alone for the rest of the app session and to the node's retention (`Group inboxes left to retention: N.`, count-only).
- Group readers (#405): the read token of `I(self,k)` derives from the device-sealed root, like a direct inbox, and the same reader set (`DirectMessageReaderSet`) runs on it. Before it reads, each sync enrols the device reader under the current root and, when the session carries `previousDeviceSealedRootKey`, first registers the new root reader through the replaced root (best effort), then prunes once per app session per inbox and root (see Reader set). A failed enrol is logged count-only and retried on the next sync; a missing inbox is created by the read. The sync always uses the current session of the group member, so a rotated root is used without a restart. `GroupConversationMailbox.cutOffRevokedReaders` bridges and prunes every readable generation inbox of each conversation in the generation log; it attempts each one and rejects with the first failure, when the new root cannot reach an inbox the replaced root still reads.
- Logs carry counts only, never a record, a key, or plaintext.
- Devices (#417): all devices of an identity read the same `I(self,k)`, each with its own reader. Before it acknowledges a page of the current generation, a sync enrols the readers of the identity's other listed devices (`DirectMessageInboxKeys.readersFor`, once per inbox and reader per app session); a failed enrol leaves the page unacknowledged. The node acknowledges per reader, so one device's acknowledgement never hides an envelope from another, and the drain rule above keeps `deleteDrained` from deleting it first. Older generations are not enrolled: a device added in a later epoch has nothing to read there.
- Limits: a removed member still holds `gen_k` and can append junk to `I(Y,k)` until it drains; the receiver rejects it. Pending key-package requests are in memory only: a reload or stop drops them, and a member asked then is asked again only by a later session's reconcile. A crash between the MLS encrypt and the outbox save loses that send.
- Receive: a record read from the 1:1 mailbox has the peer as its author. A key-package request is answered only when the peer and this identity are both on the roster; one from this identity is answered only by the device it names, while that device holds no leaf, and a device it does not name ignores it. A welcome is opened only by the device it names; any other device ignores it. It is joined only when the leaf that signed it belongs to the peer, and the peer holds a leaf in that group and may add devices under the roster, or, from this identity, when the signing device is in this identity's verified device set (#441) and the group already holds another leaf of this identity and an identity other than this one; joining also requires the roster to list the identity of every leaf, this one's included. It must be newer than the last membership of this device; MLS then rejects a replay. A commit is applied only from this identity's inbox of that conversation, and MLS rejects a forged one or one the committer may not make. Rejections are logged without the record.
- Own messages: MLS cannot open a member's own messages, so a sender stores each queued record in its own history. Every sender also appends a copy to its own `I(self,k)`, which the identity's other devices read like any message; the sender opens its copy from the plaintext it kept at encrypt time (`GroupMailboxMlsEngine.encrypt`), and history collapses it on its record tag, so the message shows once.

### Group conversation cutover

`GroupConversationMailbox` (`infrastructure/`) is the only path for a non-community group conversation: create, add, remove, leave, send, edit, delete, reaction, pin, poll, typing, identity update, history and sync. The app reaches it as `PigeonApplication.groupMessages`. The client neither writes nor reads the node's group message endpoints, and a group has no conversation key.

- Carrier (D8 = B): key-package requests, key-package responses and welcomes travel as signed, sealed `group_conversation_invitation` notifications (`GroupMailboxNotificationLink`), read by `GroupMailboxNotificationPump` every 15 s. The pump reads only notifications the node still holds as `pending`. A record must name the conversation of its letter. A request or response is timely within 5 min either side of its send time; a welcome from 30 days before now to 5 min after, and MLS also rejects a replayed one. These notifications are not shown in the notification list, and they count against the node's notification quotas (30 per minute, 10 000 stored).
- State records (#466): the pump signs a state record (`PATCH /notifications/{id}`, `PigeonNotificationsApi.update`) for every letter it decides, so the node stops serving it. `accepted`: a request this device answered, a response or welcome it consumed. `declined`: a request it refused, a welcome that fails its checks, a letter that does not open, verify or decode, names another conversation or carries no request, response or welcome, a letter that is not timely, and a replay. A letter for another device, or a response to a request this session did not send, gets no record from this device and stays pending until the device or session it is for handles it, or until it stops being timely, when any device declines it. State records belong to the identity and the node keeps the first one, so when several devices of an identity decide the same letter, the first decision stands.
- Control replay (#421, #466): this device hands each letter over at most once, across reloads and sessions. Each letter is keyed from inside its seal: its sender, conversation and type, plus the request id of a request, the SHA-256 of the key package of a response, or the epoch index and named device of a welcome. Before handing a letter over, the pump claims its key in `GroupMailboxHandledLetters` (`pigeon-group-control-<identityId>`, label `pigeon-group-control`, kind `control-letter`), sealed under the device-sealed root with the notification id and a lease, and then stores the decided state with it. The claim is an IndexedDB add-if-absent in one read-write transaction, so of two tabs reading the same letter only one hands it over. A key held under another notification id is a replay and is declined, so a replay neither creates a second key package nor resolves a pending request again; under the same id a decided state is signed again, as after a failed `PATCH`, and a claim still being handled is left alone. An entry lives until the letter stops being timely (its send time plus 5 min, or plus 30 days for a welcome), after which the time check declines the letter anyway; each run deletes expired and undecodable entries. A handling that throws, or that the control ignores, gives its claim back and is retried on the next run. A reload or crash in the middle keeps the claim until its lease ends: for a request or response that is when it stops being timely, so the letter is declined as stale rather than answered twice, and a device add's request times out (60 s) and is retried with a new request id on its next reconcile, while a member is asked again by a later session's reconcile; for a welcome it is 5 min, after which the welcome is handed over again. A claim that cannot be stored leaves the letter for the next run. Logs carry counts only. Residuals: losing the entries (a root that opens under neither the current nor the replaced root drops the rows, as does clearing site data) reopens a letter's window; another device of the same identity keeps its own entries, so it may answer an identity-wide request too; a welcome for a device that stays offline more than 30 days is declined and that device waits for the next add; a welcome refused because this device's roster read still lags the inviter's, or because a roster refresh refuses its sender, is declined and never handed over again, where a reload used to retry it; a claim is stored before the roster check, so every validly sealed welcome, a stranger's included, keeps a small entry for 30 days; a clock more than 5 min off declines honest letters; every decided letter, spam included, takes one of the identity's state records on the node.
- Roster (D15, slice 6, node `docs/design/group-roster-in-mls.md`): the roster lives in the MLS GroupContext as the library's private-use extension `GroupMailboxRosterExtension` (type `0xf421`, `docs/mls-group.md` of `@haskou/pigeon-swarm-crypto`), read and written through `GroupMailboxRosterContext`: the canonical JSON (RFC 8785) of `version` (1), `conversationId`, `creatorId`, `memberIds`, `adminIds` and `name`. Decoding is strict: the bytes must be exactly the canonical encoding of a well-formed roster, which the library checks and `GroupMailboxRoster.of` checks again (at most 48 members, `MAX_PARTICIPANTS`, see Group size; the creator a member and no admin, every admin a member). The client never calls the node's group create, members, admins or leave routes; it creates a group locally, under the id the creator's genesis derives (see Confirmation), and lists its groups from the MLS store. Every member judges each commit by the roster in force (`GroupMailboxRoster.allowsCommit`): a manager adds one identity and only its leaves; a member leaves with its own leaves, never the creator; a manager removes a member it may remove with every leaf it holds; the creator promotes or demotes one admin. Any other change, including one that rewrites the creator, the conversation or the name, is rejected, as is a tree holding a leaf whose identity the roster does not list. A roster-only commit advances `gen_k` like any other. Groups created before this change carry no roster and are not migrated: they must be re-created.
- Group size (#519): one welcome carries the whole tree to its joiners, about 570 bytes per leaf, and travels in one control record whose binary fields hold at most 40 000 bytes (`GroupMailboxControlRecord.MAX_BINARY_BYTES`, so the sealed letter stays inside the 64 KiB mailbox bucket). A group of 48 one-device identities welcoming 47 of them at once measures 39 699 bytes, and 64 identities exceed the bound, so a group holds at most 48 members (`GroupMailboxRoster.MAX_PARTICIPANTS`); the library's own `MAX_GROUP_MEMBERS` (128) is a looser bound and is never reached. Create rejects a larger group with `GroupMailboxTooLargeError` before anything is stored or sent, and so does an add to a full roster. Identities with several devices can still outgrow the welcome below 48 members: the add is then refused before its commit is queued (`GroupMailboxTooLargeError`, nothing committed or sent, the answer decided as rejected), the invitee stays on the roster without a leaf, and sync reports `outgrown`, which the open group shows as a notice until an add's welcome fits again.
- Reconcile: after create, after each membership change and on every sync, the device leading this identity's leaves compares the roster with the MLS tree. The first committer the roster ranks among the members holding a leaf removes the leaves of identities off the roster, then asks listed members holding no leaf for a key package, so members never race each other's commits. Only the device and session that asked a member take its answer and commit the add, even when another device of the identity joined meanwhile and now leads its leaves (#509). Concurrent reconciles of one conversation join the run in progress. Each identity also compares its leaves with its verified device set (the `verifiedDevices` port, `PigeonDeviceAuthorizationApi.verifiedDevices`): the credentials at the head of the identity's signed device transitions, fetched with this device's proof and replayed on the device, never the node's device list (#441). The leading device removes the leaves of revoked devices, then adds verified devices without a leaf (see Device add), and logs `Group devices reconciled: removed N, added M.` (count-only). The engine reads the same set again before each commit it makes or applies and before each welcome from its own identity, so a revoked device is refused before its leaf is removed.
- Removal gap: a removal is one commit that changes the roster and drops the leaves together, so no epoch holds an identity the roster no longer lists, except a leaver's own leaf, which its leave commit cannot drop, and leaves of strays a rank change removes. The outbox reads the roster from the group before it seals: while the tree holds an identity off the roster it encrypts nothing, and messages wait as held until a commit removes it. No commit adds a leaf while an identity off the roster holds one, as that identity would receive the commit and learn the joiner and the next generation from it: a manager first removes such leaves in a commit that adds none, and every member refuses a commit that adds a leaf while one remains (`GroupMailboxRoster.allowsCommit`). A removed device sends nothing more, not even a commit it queued, and drops the group from its list. A message from an identity off the roster is refused. The removed member cannot read another member's inbox: the node checks each read against the read-token hash the owner registered, and the read token comes from the owner's root key, not from `gen_k`. Residual: a node operator who shares envelopes with the removed member exposes them.
- Confirmation (D15, node `docs/design/group-roster-in-mls.md`, "Joiners and the welcome"): a welcome is signed by its welcomer alone, so a member could welcome this device into a tree it made up, with leaves taken from published key packages. A group joined from someone else's welcome therefore stays unconfirmed until this device applies a valid commit, or opens a valid message, from a leaf of a confirming identity. The confirming identities are fixed at the join: the creator, when this device knows the group's genesis, and every identity pinned as a contact on this device (`GroupConversationPorts.contacts`) before the welcome, other than the welcomer and this identity, whose leaf in the welcomed tree one of its own commits wrote (`leafNodeSource` other than `key_package`). Neither the welcome nor the node names the creator: the genesis `{creatorIdentityId, networkId, nonce}` (`GroupMailboxGenesis`) is the preimage of the group id, so only the creator's own genesis derives it. The creator hands it to each joiner in its key-package requests, and members pass it on in theirs. A welcome from the creator confirms the group at once (creator shortcut), as does a welcome from this identity's own device. A group this device creates is confirmed.
- Unconfirmed: the engine refuses to encrypt, add, remove or remove devices (`GroupMailboxUnconfirmedError`), reconcile commits nothing, the outbox holds every queued message unsealed and appends no queued commit, ephemeral records (typing, receipts) are dropped, and key-package requests for the group are neither sent nor answered. A sync reports `unconfirmed`, and the open group shows a notice that it is not yet verified and its messages wait; held messages show as held and are sealed in the epoch current on the first pass after the confirmation. Receiving stays open: commits apply and messages are read, which is how the confirmation arrives.
- Liveness: MLS writes no update path for an add-only commit, so a leaf only ever added keeps `leafNodeSource: key_package`, and its identity confirms only joins after it committed a removal or an update. A device welcomed by a non-creator that knows no genesis and finds no pinned contact with a self-written leaf has no confirmer and stays unconfirmed until it is removed and the creator welcomes it again. A genesis learned after the join adds no confirmer.
- Records: the confirmation is a sealed row of the MLS store, written before the joined group's state; a group without a readable record is unconfirmed with no confirmer, so it never confirms. Groups this device held before this rule, created or joined, have no record: they stay unconfirmed, send nothing and show the notice, and must be re-created (no grandfathering).
- Joiner: a member add waits for no answer. The joiner answers when its pump next reads the request, and the session that asked commits the add when its pump reads the answer, so that session must still be open then; otherwise a later session's reconcile asks again. A device add waits at most 60 s (`KEY_PACKAGE_TIMEOUT_MS`) for the device's key package, so that device must be online then; otherwise the next reconcile retries. The node stores MLS key packages only for communities, so they cannot be published ahead.
- Payload: a record's `encryptedPayload` is the plain message JSON; MLS encrypts the whole record for the current epoch. On receive, `MessageProjector.projectPlaintext` rejects a payload whose author is not the record's author. MLS cannot open a member's own messages, so the sender stores each queued record in its own history.
- Sidebar: control letters are read every 15 s and at once when a realtime `group-control` event arrives. A read whose welcome joined a group refreshes the conversation list, so the new group shows. The first group sync that finds this identity off the roster refreshes the list once, so the group leaves the sidebar.
- Background groups: `useGroupMessageBackgroundSync` covers every group on mailboxes that is not open. It first reports each one once from its stored history (`GroupConversationMailbox.activity`, no network), then every 5 s reads the inboxes of at most 2 groups into that history (`receive`), each at most once per 30 s, the least recently visited first. A visit builds no timeline and does not reconcile the roster; the open group does. A result for a group opened meanwhile is dropped. The reported count sets the sidebar badge, zero for a muted group, and a newer message time moves the group up the list. Inbox reads and history replays of one conversation run one at a time, so opening a group never misses what a background read stored meanwhile. Opening a group clears its badge, and the open group marks its history read after the restore and after each successful pass, on this device only.
- Storage: per identity, `pigeon-group-history`, `pigeon-group-outbox`, `pigeon-group-mls-<identityId>`, `pigeon-group-generations-<identityId>` and `pigeon-group-control-<identityId>`, each scoped by `scopeClientStorageKey`. The MLS store also keeps each group's confirmation and learned genesis (see Confirmation). Forgetting this device's identity (sign-out, device removal) deletes all five. A logout that keeps the device keeps the rows and drops the members held in memory, with their decrypted entries.
- No migration: a group created before the cutover is not readable and must be re-created.
- Not carried yet: thread reply counts of group conversations. Without a device-sealed root the outbox keeps its rows in memory only, so a reload drops queued and failed messages, and the history keeps nothing, so groups show no unread count.

## Creation proof

- Preimage: `[pigeon-mailbox-creation:v1, mailboxId, postTokenHash, readTokenHash, nonce].join(':')`.
- SHA-256 must start with at least `difficultyBits` zero bits. The default is 16 (`MailboxCreationProof.DEFAULT_DIFFICULTY_BITS`). A `PUT` 400 that names `requiredDifficultyBits` raises the requirement; see Creation difficulty and recovery.
- `nonce` is the first passing decimal integer from 0, at most 64 characters.
- Mining runs in a dedicated worker: `mailboxCreationWorker.ts`, driven by `MailboxCreationWorkerClient`, constructed by `createMailboxWorkerClient()`.
- Pinned nonce for the vector: `47805`.
- Shared vectors: `src/test/fixtures/mailbox-creation-proof-vectors.json` is byte-identical to the node's `tests/fixtures/mailbox-creation-proof-vectors.json` (preimage, digest, leading zero bits, mined nonce, rejected cases), checked by `MailboxCreationProof.vectors.spec.ts`.

## Envelopes

- Fixed buckets for the decoded body: 1024, 4096, 16384, 65536 bytes.
- Body = base64url(iv ‖ ciphertext ‖ tag), AES-256-GCM with the envelope key, through WebCrypto (`crypto.subtle`), so browsers use their native AES-GCM. Seal and open are asynchronous; an open that fails for any reason rejects with `MailboxEnvelopeError`, and `MailboxChannel.read` opens a page's envelopes in parallel and drops those that fail.
- AAD = `${mailboxId}.${envelopeId}`.
- Plaintext framing: u32be(length) ‖ plaintext, zero-padded to the bucket.
- `MailboxEnvelopeCipher.MAX_PLAINTEXT_BYTES` (65504) is the largest plaintext that fits: the largest bucket minus IV, tag, and length prefix.

## Creation difficulty and recovery

- `createInbox` mines at the default 16 bits. If `PUT` returns 400 with `requiredDifficultyBits`, it re-mines once at that value and retries the `PUT`. A second refusal, or a value outside 17 to 24, propagates without re-mining.
- Rate limit: the node caps creations per client address (`MAILBOX_CREATE_RATE_LIMIT_PER_MINUTE`, 30 per 60 s by default). An over-limit create returns 429, which surfaces as `HttpJsonError`. The recipient pass stops at the first 429 and reports incomplete. An inbox whose open failed, rate-limited or not, is not tried again for 60 s (`OPEN_RETRY_MS`), so creation work stays bounded per conversation. Senders never create.
- Recipient `read` and `acknowledge` re-create an evicted mailbox once on 404, with the same id and capability hashes, then retry the operation. A second 404 propagates. Both report `recreated: true` when this happened. The re-creation enrols the device reader again (`createInbox(root)`, then `addReader(device)`).
- A re-created inbox numbers its envelopes from 1 again, because node `nextCursor` starts at 1 for each mailbox. A cursor stored for the old inbox would hide new envelopes. `DirectMessageMailbox.sync` therefore re-reads from 0 when `read` reports `recreated`, and stores cursor 0 when `acknowledge` does.
- Senders (`send`) do not re-create. They lack the read-token hash, so they recover after the recipient's next read or acknowledgement.

## Receive

- Forged or undecryptable envelopes are dropped silently. Nothing about them is logged.
- The returned cursor includes dropped envelopes, so acknowledging up to it removes them.
- Logs never contain decrypted payloads or topics.

## Direct messages

- Scope: one-to-one conversations only. The mailbox is the only delivery and history path for them: the client neither writes nor reads the node's one-to-one message endpoints (see Cutover below). Group conversations are under Group conversation cutover; communities keep their node endpoints. Attachments, replies, and stickers travel as opaque encrypted payload inside the sent record.

| Kind                                    | Mailbox record                                    | Status                                                                                     |
| --------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Sent: text, reply, attachments, sticker | `sent` (`replyToMessageId` for replies)           | Carried                                                                                    |
| Edited                                  | `edited` (`targetMessageId`)                      | Carried                                                                                    |
| Deleted                                 | `deleted` (`targetMessageId`)                     | Carried                                                                                    |
| Reaction add / remove                   | `reaction` (`action`, `emoji`, `targetMessageId`) | Carried                                                                                    |

| Thread send, edit, delete, reaction     | none                                              | Not carried: thread UI is group-only. One-to-one has no threads to carry.                  |
| Pin and unpin                           | `pin` (`action`, `targetMessageId`)               | Carried. Applied last-writer-wins by `createdAt`; see Pin order.                           |

- Envelope: plaintext is `{kind:'direct-message', version:2, record}`. `record.type` is `sent`, `edited`, `deleted`, `reaction`, `pin`, or `read`. `DirectMessageMailboxRecord.decode` returns null for a wrong kind or version, a wrong conversation, missing or invalid fields, an unknown type, or a bad reaction or pin action.
- v1 `direct-text` envelopes decode to null and are acknowledged, so they do not block the inbox. They are not shown, and nothing is migrated.
- Transition: the cutover is one version step with no dual publication. A record is written only as a version 2 mailbox envelope; no v1 envelope and no legacy node copy is written next to it, and the node serves no `/conversations/{conversationId}/messages` or `/pins` routes and refuses replicated message, pin and reaction records scoped to a conversation (node `docs/api.md`, "Conversation messages"). A future version must again replace the previous one rather than publish both.
- Size: a record whose plaintext exceeds `MailboxEnvelopeCipher.MAX_PLAINTEXT_BYTES` cannot be delivered, so its send rejects. The bound applies to every kind, including a very long text message. Attachment bytes upload as private blobs first; the payload carries only their references, download tokens, expiry, the attachment key, and per-chunk IVs. Each part adds to the payload, so a message with many or large attachments is refused whole and never split across envelopes.
- Send: `directMessages.send` builds the sent record once, with the same encryption, `previousMessageIds`, `replyToMessageId`, and attachment publishing as the former legacy send. It checks that the record fits the envelope and that its conversation key resolves, persists the record in the sealed outbox (see Same-device history), and resolves with the locally projected message. A rejection means nothing was persisted, such as a missing conversation key or an over-size record. Delivery runs in the background with one drain per send, so a send to an absent inbox does not hold back other sends. The peer copy is written first, then the own copy (see Own copy). While the peer's inbox is not open yet (a 404 with no other fault, see 404), the send shows the retry state (`Retrying`) and its peer copy is retried with capped backoff. Any other fault marks the send `failed`, and the user's retry re-queues it. There is no POST to `/conversations/{id}/messages`.
- Edit, delete, reaction, and pin: `directMessages.edit`, `delete`, `reaction`, and `pin` follow the same rule, including the retry window for an absent peer inbox. Each rejects when the peer copy is still not delivered, and the UI shows the error notice. No legacy copy is written in its place.
- Own copy: after the peer copy is delivered, the same record (same id) is appended to this identity's self-inbox (the inbox the peer writes into), tagged with an authorship tag (see Authorship), so the other devices of this identity apply the change. The record is built once. An own-copy failure, including a throw while building it (for example, no root key), is logged as one count-only line. It does not reject the call and is not retried.
- Pin, reaction and delete send: the hooks call `applicationContainer.messages.pin`, `unpin`, `addReactionTo`, `removeReactionFrom` or `delete` with the conversation for both conversation types. The messages use cases (`MessagePinner`, `MessageUnpinner`, `MessageReactionAdder`, `MessageReactionRemover`, `MessageDeleter`) route on the conversation type: one-to-one writes go to the `DirectMessageRepository` port (`MailboxDirectMessageRepository`, which calls `directMessages.pin`, `reaction` or `delete`), and group writes load and save the message aggregate. The use case takes `createdAt` from `Timestamp.now()` when it runs; presentation passes no time. A rejected pin is not in the mailbox, so no other device applies it. The pinned list is not loaded from the node for one-to-one conversations (see Cutover).
- Recipient home: the append goes to `<mailboxHome>/mailboxes/...` when the recipient's identity serves a `mailboxHome` base URL (origin plus optional path prefix, published as the UI's API base) that verifies against the identity signature (`IdentityMailboxHomeVerifier`). Private hosts are rejected; `localhost` is accepted for development. Otherwise, or when the home append throws, the append goes to the connected node. Each fallback logs one count-only debug line (no URL or id). Home calls use an isolated client (`credentials: omit`, `redirect: error`). Reads and acks stay on the connected node, plus the availability servers (see Availability servers). Each send adds one identity lookup. A failed home append can still have stored the envelope, so the fallback can land the same envelope twice; the timeline collapses duplicates by message id. The published hint is last-write-wins across a user's devices.
- Recipient: the active one-to-one conversation is polled about every 5 s (`useDirectMessageMailboxSync`). Each page is decrypted in envelope order into timeline changes (`message`, `edit`, `removed`, `reaction`, `pin`, `read`), applied, then acknowledged. The cursor advances only after a successful ack. These changes are the only source of timeline, unread, and push updates for one-to-one conversations. Legacy realtime message events are ignored for them. Messages collapse by id in `MessageCollection.merge`. A sent or edited change is dropped when its message does not decrypt.
- Replay dedupe: the timeline applies each record id once. A replayed envelope whose record id is already applied adds no change (`DirectMessageTimelineSync`). That set lives in memory per mailbox instance, and restore seeds it from the store, so the store is not consulted for dedupe. Two devices of one identity keep separate sets.
- Own-copy echo: a record whose id this device appended as an own copy is acknowledged and not applied, since this device already shows it. The skip set is keyed by identity and record id and keeps the 512 most recent own copies, in memory only. After a reload the set is empty, so own records appended but not yet read are applied again. The reaction and pin clocks are also empty then, and edits and deletes have no clock, so a replay can override a later local change only when that change never reached the mailbox.
- Reaction order: a mailbox reaction applies only when its `createdAt` is newer than the newest write seen for the same message, author, and emoji. A remove leaves its clock on the message (`reactionClocks`), so a replayed older add cannot reopen the reaction. Local writes apply in arrival order and advance the same clock. The clock is timeline state: it survives a same-id merge but not a reload. After a reload a reaction can reopen only if its remove was never appended to the mailbox, or was acknowledged before an add that was appended later. Mailbox writes use the sender's `createdAt`, so ordering across devices assumes their clocks agree to within the gap between the two actions.
- Pin order: a mailbox `pin` change applies only when its `createdAt` is newer than the last applied change for the same message, so a replayed or out-of-order record cannot undo a newer one. Within one pass, changes apply in order. Before the comparison, each `createdAt` is clamped to at most 30 s after the time the pass applies it (`MessagePinChange.clampedTo`), so a member who dates a pin far into the future cannot hold it against every later change; a later honest change wins once its own `createdAt` passes the clamped value. Older dates are kept, so changes delivered late keep their order. The same clamp applies to one-to-one and group pins. The messages domain policy `MessagePinClock` owns this rule (`admit` clamps and keeps the winning changes, `applyTo` computes the next pinned set); the sync effect holds one clock per run and only applies its output. The clock resets when the conversation or session changes. A pin change updates only the pinned set, never the timeline.
- Pin residual risk: local pin writes do not advance the pin clock. A mailbox pin or unpin applied after a local change to the same message can override that local state. There is no `listPins` load for one-to-one conversations, so nothing from the node corrects it.
- Read receipts: `directMessages.markRead` appends a `read` record (`targetMessageId` is the last delivered message restored) to this identity's own inbox. It replaces the node read-until call for one-to-one conversations. Opening a one-to-one conversation marks it read once its stored history is restored (`useDirectMessageMailboxSync` hands the restored messages to `onHistoryRestored`). It is best effort: it never rejects and never shows an error, and a failure is logged count-only. It runs only for the active one-to-one conversation, once per read mark, with no dedupe; each record is small. The peer's inbox is never written. The timeline hands every read to one use case, `conversations.markReadUntil` with the open conversation; `ConversationReadMarker` (conversations application) routes a read of the open one-to-one conversation to `ConversationReadReceiptRepository` (`MailboxConversationReadReceiptRepository`, which calls `directMessages.markRead`). Every other read, including every group read, stays on this device and makes no node call.
- Read receipt apply: the active sync hook and the background pass (`useDirectMessageBackgroundReadSync`) apply a fresh `read` record from this identity's inbox by calling `onConversationRead`, which clears unread for that conversation on this device. The timeline is unchanged. Records from other authors are acknowledged and ignored.
- Freshness: a `read` record applies only when `createdAt` is at most 14 days old and at most 30 s ahead of the local clock, matching the node's `MessageReadProof` limits. Both edges are inclusive. Stale or future-dated records are acknowledged and ignored.
- Trust: a `read` record is authenticated by the conversation key and, when this identity authored it, by its authorship tag (see Authorship). The peer holds the conversation secret, which derives this identity's self-inbox keys, but not the root key. A receipt it writes as this identity is dropped, so it cannot clear this identity's own unread state.
- Authorship: a record whose `authorId` is this identity is applied only when its envelope carries `authorTag`: HKDF-SHA256 (no salt, 32 bytes) over the device-sealed root (`sessionRootKey(session)`, which throws without one), with the label `pigeon/mailbox/own-record/v1` followed by the record's JSON with keys sorted. Only the own-inbox copy is tagged. The peer copy and records from other authors need no tag. The sync path and the background read pass both check the tag, so a record that claims this identity without a valid tag is acknowledged and dropped. A peer that writes into the self-inbox cannot forge or replay a sent, edited, deleted, reaction, pin, or read record as this identity.
- Authorship residual: the sender needs its root key to tag its own copy, which it already holds for reads. An own copy that cannot be tagged (no root key) or exceeds the envelope bound is not written, and the send still resolves on the peer copy.
- Authorship rollout: own copies written before this change carry no tag, so upgraded devices drop them on read. Peer copies are unchanged and the envelope version stays 2, so no version bump is needed. Pre-upgrade own records are not replayed to other devices of this identity.
- Background pass: `useDirectMessageBackgroundReadSync` clears unread on the other one-to-one conversations with `unreadCount > 0`, so a read on another device shows here. Each tick (5 s) visits at most 2 conversations, and each conversation is visited at most once per 30 s. A visit reads at most 4 pages of 50 envelopes. It never acknowledges, writes the shared cursor, or creates an inbox, and it skips an inbox this device has not opened. A clear applies only when the visit reaches the end of the inbox and no sent message from another identity follows the last fresh own read, so an unread message is never hidden. A visit that hits the page limit clears nothing and retries on a later pass. The active conversation is never visited by this pass. On the active sync path, a delayed older `read` can still clear unread for a newer message that arrived after it.
- Pre-create: the recipient inbox of every one-to-one conversation this identity holds a key for is opened (created, device reader enrolled) on session start and whenever the session or the conversation list changes (`useDirectMessageInboxPrewarm`, which calls `DirectMessageMailbox.openInboxes`), not only for the active conversation. Opens run one at a time and skip inboxes already open. A pass that leaves an inbox unopened, or rejects, is retried after 60 s. The sync path opens the active inbox the same way before its first read. Overlapping passes share one creation (`MailboxChannel.createInbox`), so a StrictMode remount sends one PUT. A failure is silent; the read's 404 recovery covers it on the next pass.
- Open marker: `{cursor: 0}` is stored only after the device reader is enrolled. A failed or rate-limited open stores nothing, so the next open retries it instead of skipping it.
- A 404 on append means the node holding the inbox has no inbox for this recipient. A 404 from the recipient's home falls back to the connected node. A 404 there with no other fault seen means the peer has not opened the conversation yet, or its inbox was evicted and not re-created. A send retries its peer copy with capped backoff (250 ms doubling to 4 s) for 30 seconds, then every 60 seconds, for as long as the session lives (see Send). Edit, delete, reaction, and pin retry the peer copy with the same backoff for 30 seconds; if the inbox still does not exist, the call rejects and the user's retry is the only retry after that. A home lookup failure, or a home append that is not a 404, is a fault: a send then marks itself `failed`, and the other writes reject at once with no retry. The own copy gets the same 404 until a device of this identity has opened the conversation's self-inbox. It is then not written and not retried, and the send still completes on the peer copy.
- A failing sync shows one notice unless another error is already shown. The next successful pass clears only that notice.
- The cursor is stored in localStorage under `pigeon.direct-mailbox.<mailboxId>` (scoped per client). Both reader tokens are derived, so clearing storage loses only the cursor. The background pass keeps its own read cursor under `pigeon.direct-mailbox-read.<mailboxId>`, so it never moves the shared cursor.
- A stored cursor is reset to 0 when the inbox is re-created (see Creation difficulty and recovery).
- Gaps: polling only (no realtime hint); no retry beyond the next poll; epoch fixed at 0.
- Multi-device: each device reads and acknowledges with its own device reader, and the node keeps an envelope until every reader has acknowledged it. An ack from one device therefore cannot remove a message another device has not read. The reader set holds at most `maxReaders` readers per inbox (129 by default: the root plus 128 devices), so a device past the cap cannot enrol (see Reader set).

### Cutover: node 1:1 path retired

The mailbox is the only delivery and history path for one-to-one conversations. No shim, fallback, feature flag, or history migration remains. The client neither writes to nor reads the node's one-to-one message endpoints. Groups moved to their MLS mailboxes (see Group conversation cutover), and the node's message collections are gone (see Node message collections retired). Communities keep their node endpoints.

- Removed for one-to-one:
  - Send, edit, delete, reactions (add and remove), pin, unpin, and the pin list (`listPins`).
  - `read-until` (`conversations.markReadUntil`). Its replacement is the own-inbox `read` record.
  - `loadAround` and `loadThread` for one-to-one conversations. The reply-target fetch shows an error, and threads are group-only.
  - Realtime message events for one-to-one conversation ids.
  - The copy model: the additive copy written after each legacy one-to-one write, its separate delivery outcome, its side-effect helper, and the copy notice that reported a failed copy. The own copy now follows the peer copy and shares its record id; a failed own copy is only logged (see Own copy).
  - The message POST as a carrier of 1:1 attachments. They reach the peer only through mailbox records. The attachment downloader's legacy methods stay, because group and community history use them.
  - The timeline message list (`messages.load`, on open and on older pages) and latest-message recovery (`PigeonConversationRepository`) for one-to-one conversations. `useConversationTimeline` builds a one-to-one timeline only from the mailbox restore and sync, and keeps it on a resume. Latest-message recovery is gone for groups too (see Node message collections retired).

- Accepted losses (decided; not backfilled):
  - One-to-one history is never loaded from the node. Mailbox envelopes are deleted on full acknowledgement, so a 1:1 message that is in neither the local history store nor the projection cache is gone after a reload. The local store is described in Same-device history.
  - No backfill for restored devices. A device paired from an authorized device receives that device's stored one-to-one history (see Pairing history export), within the history policy chosen at pairing and the export caps. A post-cutover own copy reaches only devices that read the self-inbox within the node's 14-day retention. Messages written to the node's one-to-one endpoints before the cutover are no longer shown. Design: `docs/design/own-copy-and-history-backfill.md`.
  - A 1:1 send to a peer whose inbox is not open yet is retried until its peer copy lands, with no give-up while the session lives. It survives a reload and sign-out through the sealed outbox and resumes on unlock (see Same-device history). Sends in the same conversation no longer queue behind a pending one, so concurrent sends share a predecessor and appear as siblings. A forget that runs while a peer copy is in flight can still leave that copy on the peer's inbox, and the attachment blobs of a forgotten send remain until the node's retention removes them. A send whose peer copy lands but whose `peerDelivered` flag is not saved before a stop or reload is appended again on resume; the recipient's timeline collapses messages by id.
  - Edit, delete, reaction, and pin are rejected when the peer copy is not delivered, and the UI shows the error notice.
  - Read receipts never block and never show errors. A failed receipt is not retried; the next read mark sends a new one.
  - Pinned state after a reload comes only from pin records still in the mailbox and from the local cache.
  - v1 `direct-text` messages are not shown. Own copies written before the authorship change are dropped on read (see Authorship rollout).

- Open risks (caveats; not addressed by this cutover):
  - Oversized records have no mailbox copy: a record above `MailboxEnvelopeCipher.MAX_PLAINTEXT_BYTES` is refused and its send rejects. Attachment-heavy messages need a split or a larger bound first.
  - Attachment references carry `expiresAt`. How node blob lifetime compares with the 14-day mailbox retention was not checked.
  - Retention: an envelope not acknowledged by every reader expires after the node's retention (14 days by default). A device that stays away longer loses those messages.
  - Silent or evicted readers can fill an inbox. Appends then return 409, and every one-to-one send to that inbox fails until the reader is pruned or the envelopes expire.
  - Reader cap: 128 devices per identity. An extra device has no read path for the inbox.
  - Own copies double the envelopes in this identity's self-inbox. A full self-inbox refuses both the own copy and the peer's sends into it, so a stuck own device blocks the peer too.
  - A failed own copy is not retried, so the other devices of this identity miss that change.

### Node message collections retired

The UI side of haskou/pigeon-swarm-node#289: the node no longer replicates one-to-one or group messages, reactions, pins or read markers, and it cannot know the read state of sealed content. Conversation metadata stays on the node for one-to-one conversations: create, list and drafts (`/conversations`, `/conversations/me/drafts`, `/conversations/me/drafts/{draftKey}`). The node no longer serves a conversation frontier (haskou/pigeon-swarm-node#555), so `ScopeFrontierReader` reads community frontiers only. A group's roster, creation and list live in MLS (see Roster).

- Removed HTTP: the conversation message list, send, edit, delete, `around`, `thread`, pins, reactions and `messages/read-until` (`PigeonMessagesGateway`, the message methods of `PigeonMessagesApi` and `PigeonMessageCommandsApi`, `PigeonConversationsApi.markReadUntil`). `PigeonConversationDraftsApi` keeps the drafts. `PigeonMessageCommandsApi` keeps only the record builders the mailboxes use (`withSentRecord`, `composeEdit`), and `PigeonLinkPreviewsApi` serves link previews directly.
- Removed realtime: `conversations.v1.message.*` (sent, edited, deleted, `was_pinned`, `was_unpinned`, `reaction.*`) and `conversations.v1.messages.were_read`. `ConversationRealtimeEvent` handles only `conversations.v1.conversation.*` lifecycle events and `conversations.v1.call.event.was_recorded`.
- Removed push: the `notifications_cleared` push type with its `tags` field.
- Unread: `ConversationResource` and the `Conversation` aggregate carry no unread count, and the aggregate records no read event. The count lives only in presentation state (`useUnreadMessages`, `ConversationWithUnread`) on this device. A recorded call event that notifies raises it; one-to-one read records and opening a conversation clear it.
- Group unread: a group's count comes from its sealed read marker in the local history (see Group unread in Send and receive) and is added to any call-event count by `useUnreadMessages.setGroupUnread`. Groups that are not open are kept current by `useGroupMessageBackgroundSync`; read state is per device, so a read on another device does not clear it here.
- Latest activity: `latestMessageAt` comes from the node's conversation list, and for a group also from the newest message in its local history, whichever is later.
- Polls (#466): a group poll lives only in the group's MLS records; the node never sees it, and its polls API takes community channel polls only. Three records carry it: `poll` (`id`, `question`, `options` of 2 to 10 with distinct ids, `allowsMultipleVotes`; the record id is the poll id), `poll_vote` (`targetPollId`, `optionIds`; an empty list removes the vote) and `poll_close` (`targetPollId`). `GroupConversationMailbox.createPoll`, `votePoll` and `closePoll` queue them like a message; `createPoll` checks the poll first (`PollBoard.canonical`), so an invalid one is never queued. On receive, a `poll` id must be bound to its MLS sender and not held by another author, like a message id; a `poll_close` is accepted only from the author of its poll; any member may vote. Records carry no message, so they never count as unread and leave the message timeline untouched. `useConversationPolls` folds the poll changes of the sync hook into one `PollBoard` per conversation: the first poll per id wins; each member's newest vote (by `createdAt`) counts and must name options of the poll, one unless it allows several; only the creator closes, the earliest close wins, and votes dated after it are dropped. Vote and close times are clamped to at most 30 s after they are applied, as for pins. A vote or close that arrives before its poll waits in memory until the poll arrives. Residuals: the board lives in memory and is rebuilt from history on reload, so a poll older than the restored history page (`HISTORY_PAGE`, the newest 50 records) is not shown; the waiting votes and closes are not bounded per session.
- Drafts (#466): a one-to-one or group draft is stored on the node under an opaque key, so the node never learns which conversation it belongs to and checks no roster. `ConversationDraftCipher` derives `K_draft = HKDF-SHA256(sessionRootKey, salt: none, info: "pigeon/conversation-draft-key/v1", 32)` and `draftKey = base64url(HMAC-SHA256(K_draft, utf8(conversationId)))` (43 characters, unpadded). The payload `{ content, conversationId }` is sealed under the device-sealed root with the associated data `pigeon/conversation-draft/v1:<draftKey>`. `PigeonConversationDraftsApi` saves with `PUT /conversations/me/drafts/{draftKey}`, deletes with `DELETE` on the same path and lists `GET /conversations/me/drafts`; a listed draft is kept only when it opens under its key and its sealed conversation id derives that same key, so the node cannot move a draft to another conversation. A save returns the payload and time it sent, never the node's echo. The node keeps 100 drafts per identity and evicts the oldest. Residuals: `updatedAt` and the set of drafts are not authenticated, so the node can roll a draft back to an older sealed version of the same conversation, withhold, delete or reorder drafts; it still sees their count, sizes and timing. After a root rotation old drafts no longer open and stay on the node until evicted.
- Typing (#466): a group conversation's typing indicator is a `typing` record (`id`, `authorId`, `conversationId`, `createdAt`; no other field) sealed in the current MLS epoch, never the node's realtime relay, which now relays typing for one-to-one conversations only; community channels keep the relay. `GroupConversationMailbox.typing` sends it at most once per 10 s per member and conversation (`GroupConversationSender`), counting attempts that were dropped, and only when the composer turns active: there is no stop record. `GroupMailboxOutbox.sendEphemeral` encrypts it and appends one copy to every other member's inbox right away: it is never queued, stored in `items`, retried or sent to this identity's own devices, nothing is sent while a removal is pending, and a member that an earlier queued record still waits for is skipped, so it never reads an epoch it has not reached. A skipped or dropped copy still advances the sender's MLS ratchet, and a receiver ratchets at most 200 generations forward (ts-mls `maximumForwardRatchetSteps`), so no typing record is sealed in a conversation once one of its queued records has waited longer than 15 minutes (`EPHEMERAL_HOLD_MS`): a held member's gap stays below 100 generations. It is bound to its MLS sender like any record but needs no claim; `GroupMailboxInboxSync` hands it to the timeline yet never appends it to the local history, so it never shows in history, unread or a restore. `useGroupMessageMailboxSync` routes the `typing` changes, with the `message` changes that end them, to `useWorkspaceTyping.receiveGroupTyping` (`applyGroupTypingChanges`): the author shows as typing until `min(createdAt, now) + 15 s`, a notice already past that is ignored, and a message from the author clears it. Residuals: each notice counts against an offline member's inbox append rate and 1000-envelope depth (D17), so a long typing session can fill an absent member's inbox sooner; a member whose inbox refuses appends while the others type for more than about 30 minutes without sending anything (a sent message is queued, so the hold applies) could miss that sender's next message, as the gap then passes 200; a one-to-one mailbox decodes a `typing` record but ignores it, and its sync still stores it like any other unknown-to-the-timeline record.
- Identity updates (#466, slice 4 of the node's `docs/design/group-roster-in-mls.md`): the node no longer tells group co-members of an identity update (`identities.v1.identity.was_updated`) or shows them each other's presence; it does so only for one-to-one participants and community members. A group member instead announces its own update as an `identity_updated` record (`id`, `authorId`, `conversationId`, `createdAt`; no other field) sealed in the current MLS epoch. After a profile save, `ProfileEditor` calls `announceIdentityUpdate`, which sends `GroupConversationMailbox.identityUpdated` to every group conversation in the list; a failing group leaves the others announced. It is ephemeral like `typing`: `GroupMailboxOutbox.sendEphemeral` seals and appends it once, never queued, kept or retried, with the same removal and hold rules. It is bound to its MLS sender like any record but needs no claim, and names no identity of its own: a receiver refreshes only the author. `GroupMailboxInboxSync` hands it to the timeline as an `identity_updated` change but never appends it to the local history. `useGroupMessageMailboxSync` routes it to `onIdentityUpdated`, and `GlassWorkspace` refreshes the author's identity from the node (`identities.refresh`, signature-checked) and remembers it. Presence of others is shown only from end-to-end presence inboxes (`useWorkspacePresence`), so nothing in the client expected node presence from group co-members. `useGroupMessageBackgroundSync` hands it on the same way from a group that is not open (`GroupConversationMailbox.receive`). Residuals: a background group is visited at most once per 30 s, so a member may show the old profile until then; a member offline past the inbox retention misses the update until it next reads the identity; a one-to-one mailbox decodes an `identity_updated` record but ignores it.

## Availability servers

Client side of haskou/pigeon-swarm-node#290: a direct inbox is kept on several nodes, so a message still lands and reads while the recipient's home is down.

- Config: `VITE_MAILBOX_AVAILABILITY_SERVERS` is a comma-separated list of API bases, set per deployment (`MailboxAvailabilityServers.pick`). Each entry resolves against the page origin as `VITE_API_SERVER_URL` does and is kept only when it is a publishable mailbox base (`MailboxHomeBase`: no private hosts; `localhost` for development). Repeats and the connected node are skipped, and at most 3 are kept. Unset means no availability servers, and the client behaves as before. Each server is reached through an isolated client (`credentials: omit`, `redirect: error`).
- Open: the sync pass and `openInboxes` open the own inbox on the connected node first, then on each picked server, with the same creation proof, device reader, and retry window. Each server keeps its own cursor and open marker under `pigeon.direct-mailbox.<base>:<mailboxId>` (`DirectMessageMailboxStore(base)`), so the servers never share a cursor.
- Announcement: after each sync pass, even a failed one, the recipient tells the peer which picked servers hold its inbox open, when that list changed since its last announcement. The announcement is one envelope in the peer's inbox, sealed by the conversation key like any record: plaintext `{kind:'direct-mailbox-servers', version:1, authorId, conversationId, createdAt, servers}` (`DirectMessageAvailabilityAnnouncement`). The last list sent is stored under `pigeon.direct-mailbox-announced.<mailboxId>`. A failed announcement is retried after 60 s (`OPEN_RETRY_MS`) and logs one count-only line.
- Trust: the receiver keeps an announcement only when it decodes, names this conversation, and its `authorId` is the conversation peer; `servers` must be at most 3 distinct canonical publishable bases. Anything else is acknowledged and ignored. Lists apply last-writer-wins by `createdAt`: an announcement not newer than the stored one is ignored. The list is stored under `pigeon.direct-mailbox-servers.<peerMailboxId>`. The announcement is not a timeline change.
- Fan-out: every append to the peer's inbox (sends, edits, deletes, reactions, pins, announcements) goes to the primary route (verified home, else the connected node; see Recipient home) and to each server the peer announced, in parallel, with one envelope id (`RecipientMailboxRouter.send`). Own copies go to this device's picked servers the same way. The call resolves when the primary or any server stores the envelope; it rejects with the primary error only when every target fails. Each failed server append logs one count-only line.
- Read and dedupe: the sync pass reads the connected node, then each picked server, through the same decrypt, apply, and ack path. One record arrives once per server, and the timeline applies each record id once (see Replay dedupe). A server is read only once its inbox is open there. A failed server read logs one count-only line and does not stop the other reads; a failed connected-node read still rejects the pass after the servers were read. A page a server's read cannot store is not acknowledged on that server (see Storage full), and the pass rejects with `DirectMessageHistoryStorageError` in place of any connected-node error, so the sync notice shows.
- Release, pairing, and revoke: `releaseDeviceReaders` removes this device's reader, `enrolDeviceReader` enrols a paired device's reader, and `cutOffRevokedReaders` cuts a revoked device off, each on the connected node and on every picked server.

### Availability residual risks

- Only the timeline sync and own-inbox appends use the servers. The realtime hint target, the background read pass (`syncReads`), and the pairing history transfer stay on the connected node.
- Each sync pass prunes the readers on every picked server it opens, once per app session per mailbox and root, as on the connected node. A server whose inbox does not open in an app session keeps a removed device's reader until a later session prunes it or the node's retention expires the inbox.
- A peer chooses which public hosts, up to 3, receive appends to its inbox. Those hosts see the same opaque envelopes and mailbox ids as the home does.
- There is no per-user picker: the servers are deployment config only.
- A server that is down is retried on every sync pass and every append; only its failures are logged.

## Contact presence

Client side of haskou/pigeon-swarm-ui#453, built on the mailbox routes of haskou/pigeon-swarm-node#552. A contact's status travels end to end encrypted through opaque mailboxes; the node sees an inbox id and ciphertext only.

- Opt-in: one switch per direct conversation in its actions menu (Share status / Stop sharing status), off by default. Sharing is mutual: turning it on sends this identity's status to the peer and opens this identity's presence inbox for that peer. Group conversations and community members have no switch, so they show no presence.
- Choice storage: the shared conversations are kept on this device only, sealed by the device key (`SealedPresenceSharingRepository`, kind `presence-sharing`, entry id = conversation id). Other devices of the identity do not inherit the choice.
- Keys (`ContactPresenceInboxKeys`): HKDF-SHA256 (no salt, 32 bytes) over the conversation key with info `pigeon/contact-presence/v1`, then the mailbox key schedule for the recipient identity at epoch 0. The presence inboxes share no id or key with the message inboxes.
- Reader: the only reader is the read token derived from the identity's device-sealed root, shared by its devices. No device reader is enrolled. A revoke rotates the root; `revokeOtherDevice` then runs `identities.cutOffRevokedPresenceReaders`, which leaves the rotated root as the only reader of every presence inbox, and reports a failed cut-off like the message cut-offs. A create answered 409 by an inbox still held under the previous root is bridged through that root and pruned to the new one.
- Record: the plaintext is `{kind:'contact-presence', version:1, authorId, conversationId, expiresAt, sentAt, sequence, source, status}` (`ContactPresenceRecord`), sealed by `MailboxChannel` under a random envelope id and appended through `RecipientMailboxRouter.send` (primary route only). `source` is a random per-app-session id that orders updates from several devices; there is no node id, network id, custom message or activity time. Decoding is strict: another field, kind or version, another conversation, or an author other than the peer drops the record.
- Send: `ContactPresencePublisher` sends `available`, `away` or `busy` at most every 10 s on a change and refreshes every 45 s; `invisible` and `disconnected` send nothing. Each update expires 90 s after it was sent (`ContactPresence.LIFETIME`). After a 404 or 409 the sender stops writing to that contact for 2 minutes. A relay failure never rejects.
- Receive: the workspace reads the presence inboxes every 30 s and re-evaluates the held updates every 5 s, so an expired update shows `disconnected` and a stale `available` never persists. Each device keeps its read position in memory and acknowledges only up to the first update still current, so the identity's other devices read it too.
- Same view everywhere: the status comes only from the presence inbox, so a contact sees the same status whether both identities use the same node or not. Presence of other identities from the node is not shown: `PigeonPresenceApi` keeps only this identity's own status (`getPresence`, `updatePresence`), the multi-identity presence search is removed, and realtime presence events about other identities are ignored.
- Stop: turning the switch off forgets the choice and deletes this identity's presence inbox for that peer (`MailboxChannel.deleteInbox`). Logout drops every held update and inbox position (`identities.disposeContactPresence`). A removed device erases its sharing choices and held presence (`identities.forgetContactPresence`, see `eraseRemovedDevice`).
- Residuals: the choice is device-local; appends use the primary route only, not the availability servers; polling only, no realtime hint; an update can be replayed within its 90 s lifetime after a reload clears the in-memory sequence; the node keeps an expired envelope until the inbox is acknowledged or its retention runs out.

## Same-device history

- Store: each stored record of a one-to-one conversation (sent, edited, deleted, reaction, pin; read receipts are never stored) is kept in IndexedDB (`pigeon-direct-history`, scoped by `scopeClientStorageKey`), sealed with AES-256-GCM. The key is HKDF-SHA256 over the device-sealed root, with info `pigeon-direct-history:v1:<identityId>`. A per-identity canary detects a root rotation, such as after a device revoke or forget: a mismatch, or a missing canary while rows exist, wipes that identity's rows. The wipe is remembered in memory and reported by `DirectMessageMailbox.checkHistoryDropped(session)` until `acknowledgeHistoryDropped(identityId)`; a deliberate `forgetHistory` is not reported.
- Outbox: a one-to-one send not yet delivered to both inboxes is one row in IndexedDB (`pigeon-direct-outbox`, scoped by `scopeClientStorageKey`). The row holds the built record and the peer id, sealed with AES-256-GCM under a key derived by HKDF-SHA256 over the device-sealed root, with info `pigeon-direct-outbox:v1:<identityId>`. A per-identity canary tells whether the rows are sealed under the session's root (`DeviceSealedRowStore`, also behind the group outbox and the contact directory). Under the replaced root (`previousDeviceSealedRootKey`, after a revoke) every row of the identity is re-sealed under the new root in one transaction, so pending sends survive the rotation; a row that does not open is dropped, and the log line gives only the re-sealed and dropped counts. A failure midway aborts the transaction, so every row stays under the replaced root and the next load retries. The canary record also lists the latest 16 roots the session replaced (`MAX_RETIRED`), each as a canary sealed under that root's keys (never the root itself), so a listed root is refused in every tab and store instance, and a stale session cannot drop the newer rows. The record also keeps the generation of the sealed-root publication its root came from (`deviceSealedRootGeneration` on the session, set by `DeviceSealedRootRotation` when it publishes or opens an entry). The node accepts only a strictly greater generation per identity, so a session whose root was published at a generation the record's does not exceed is refused and the newer rows are kept, as for a stale tab on R2 that meets the R3 canary of a re-login or a recovery on the same identity. Under neither root with a newer generation, as for a device that missed more than one rotation, the identity's rows are wiped and the dropped canary's root is listed. When either generation is unknown (a record written before this change, or a session that holds none), the rows are wiped and the dropped canary's root is not listed, since it may be the root another session uses now; the first session with a generation that opens such a record stamps it. The replaced root a session names is always listed. A root evicted from the 16 is no longer refused and, under neither root without a known order, wipes the rows. Every write (the canary renewal, the re-seal, the listing, the generation stamp, and each `save`) re-reads the canary in its own read-write transaction and decides on it there, so two tabs that first read the identity at once never wipe each other's rows, and a save never lands under a root another tab replaced in the meantime. A load reads the canary and the rows in one transaction, or in the read-write transaction that settles the canary, so it never returns a list cut short by a re-seal in another tab. The row is saved before the first delivery attempt and records `peerDelivered` once the peer copy lands, so a resume repeats only the own copy. Unlock loads every row and drains the pending ones (`DirectMessageMailbox.resumeOutbox`); sign-out stops the in-memory drain and keeps the rows (`stopOutbox`). A `failed` row stays until the user retries it or the device is forgotten. Without a device-sealed root nothing is stored. Forget wipes the identity's rows (`cancelOutbox`) after the device revocation succeeds, also when the unlock removal fails. A failed revocation keeps them; forget also drops the canary record with its list, so a stale root afterwards starts a clean store.
- Write: the sync pass appends each page's records before it acknowledges the page, own copies included. Entries dedupe on the record id the sender mints once per action, so a replayed envelope adds nothing and each reaction add, remove, or re-add keeps its own row. The id is stored in clear for the index; no digest of the content is kept.
- Storage full: a failed write, such as an exhausted browser quota, rejects with `DirectMessageHistoryStorageError`, which carries no content. The pass still shows the page but does not acknowledge it, so the node keeps its envelopes and the cursor stays. The sync notice says the messages could not be saved on this device and stay on the server for up to 14 days. Each poll reads the same page again, retries the write, and acknowledges it once the write succeeds; the replayed records are already applied, so nothing shows twice. While the write fails, each pass also reads one page past the furthest page shown (read-ahead) and shows it, so later messages still appear, one page of 50 per poll. A read-ahead page is neither stored nor acknowledged, so the history keeps the inbox order (a deletion is never stored before the message it removes); once the unstored page stores, the following pages are stored and acknowledged in turn, one per pass. The read-ahead cursor lives in memory per server and mailbox, so after a reload the pages past the unstored one are read and shown again from the stored cursor; a re-created inbox drops it. A failed read-ahead read logs one count-only line and the pass still rejects with the storage error. An envelope left unstored past the node's retention (14 days by default) is lost. Unlock refuses a session without a device-sealed root, so the store always derives its key from one; a missing root is a fault and rejects the write like a failed one.
- Restore: the first sync pass per session and conversation first replays the stored records in stored order (`DirectMessageMailbox.restore`), then runs the normal pass. The replayed records count as applied, so the pass skips them. Logout keeps the store, so re-login shows the history again.
- Deletion and replay: a removed message stays removed. If the sender re-posts the envelope of a message the timeline already applied, its record id is in the applied set (seeded by restore after a reload), so the replay adds no change and the message does not return. No spec covers this case yet; it follows from the applied-set rule above.
- Forget: `forgetHistory(identityId)` wipes the identity's rows once the device revocation succeeds, including when the unlock removal fails and for a confirmed only-device forget. A failed revocation keeps them.
- Revoked from another device: the device verifies the removal from the signed transitions (`DeviceRemovedError`, see `local-unlock.md`, "Revoked device on unlock") on its next sign-in and, while it stays signed in, every 30 seconds (`DeviceRemovalWatch.CHECK_INTERVAL_MS`), so a signed-in device notices a revoke within 30 seconds plus one transitions read while the node serves the log. A node answer alone (401, 404, 409, a timeout, or a log that does not replay) never counts; in a session it is ignored and the next read tries again. On a verified removal `eraseRemovedDevice` runs without asking, from the sign-in screen or, for a signed-in device, once the session has stopped its outboxes, realtime connections and workers and the workspace has unmounted: it wipes the identity's outbox rows (`cancelOutbox`), direct history rows and canary (`forgetHistory`), group history (`groupMessages.forget`), MLS state (`mls.forget`), the contact directory (`identities.forgetContacts`), decrypted message projections (`clearProjectedMessageCaches`), pending device-sealed recovery records (`discardDeviceSealedRecovery`), and drafts and workspace state in localStorage, then removes the vault record with the identity key material, then forgets the remembered sign-in identity when it is this one. The login screen then says the device was removed. Each step runs even when another fails. If a step rejects, the screen says the messages could not be erased and the vault record and remembered identity stay, so the next sign-in proves the removal again and retries. As on forget, the history and outbox stores log an IndexedDB failure without content and do not reject. A node can delay the wipe past the bound by withholding the transitions or refusing the read.
- Device storage: after unlock the workspace asks the browser once, without a prompt of its own, to keep the site's data (`navigator.storage.persist()`, only when not already persisted; `DeviceStorage.protect`). It then shows one dismissible notice: that the stored history was cleared (`checkHistoryDropped` of the direct and of the group mailbox, both asked at once so one notice takes both drops), or else that space is low (`DeviceStorage.estimate`: under 50 MiB free or at least 90% of the quota used). Nothing is shown otherwise. Both drops are acknowledged (`acknowledgeHistoryDropped`) only once the notice is shown: a workspace unmounted before the checks answer acknowledges nothing, and the next mount in the same app session shows the notice. A drop is kept in memory only, so a reload before the notice loses it. A group history drop is found when the check opens the group store under the new root, so it is reported on the unlock after the root change even before a group is opened. A device revoke re-seals group history from `previousDeviceSealedRootKey`, as the outbox is, so it reports no drop. Profile, Security, "Storage on this device" shows usage and quota, whether the data is persisted, and what is kept on this device, on the server (up to 14 days), and with other people. When the browser cleared the whole site, the vault is gone too, and sign-in says so (`auth.localDeviceMissing`). Browser eviction cannot clear the history or the outbox while keeping the vault: every store, the vault included, is in the origin's default storage bucket (the app uses no `navigator.storageBuckets`), and the [Storage Standard](https://storage.spec.whatwg.org/#management) requires a bucket the browser clears to be cleared in its entirety. Only a deliberate deletion of one database, as from developer tools, removes a store alone; that is not detected, and the store starts empty. Envelopes already acknowledged are no longer on the server.
- Contact directory: the display names the node already returned for other identities (conversation peers and participants, notification and membership-request identities, and profiles the session looked up) are kept in IndexedDB (`pigeon-contact-directory`, scoped by `scopeClientStorageKey`, `ContactDirectoryStore` on `DeviceSealedRowStore`), so already-synchronized contacts stay readable and searchable in the sidebar while profile reads fail. The whole directory of an identity is one row, sealed with AES-256-GCM under a key derived by HKDF-SHA256 over the device-sealed root with info `pigeon-contact-directory:v1:<identityId>`, so neither a name nor a contact id is readable at rest, including in the row keys. It holds names only: no keys, handles or pictures, and nothing cryptographic reads it; profiles, safety numbers and keys still come only from the node. At most the 1000 most recently seen contacts are kept, stamped by day, so the row is rewritten when a name changes or once a day. A stored name fills only a contact the session has not named yet or names by its raw id; a failed profile read keeps the name already shown and is retried on the next 5-minute or focus refresh instead of in a loop. A revoke re-seals the directory under the new root and any other root change wipes it, as in the outbox; forget (`CurrentDeviceForgetter`) and a verified removal (`eraseRemovedDevice`) erase it. Signing in still needs the node, which serves the device-sealed root, so this covers the node becoming unreachable after unlock, not an offline unlock.
- Not covered: envelopes acknowledged before this change were never stored, and the node has deleted them, so they are not restored.

## Pairing history export

- Trigger: before it authorizes a new device, the authorizer publishes its stored one-to-one history into a transfer inbox (`DirectMessageHistoryTransfer.publish`). Without a device-sealed root nothing is written or read, so nothing is exported. The secret is 32 random bytes per pairing. It travels inside the encrypted pairing completion as `historyTransferSecret`, which every completion carries: `DevicePairingCompletion.open` refuses material without it as `invalid`.
- Node view: the transfer inbox is keyed from the secret (`MailboxKeySchedule.derive(secret, identityId, 0)`), and its read token is `MailboxReadToken.derive(secret, mailboxId)`. The node sees the mailbox id and the hashes of the post and read tokens, never record plaintext or the secret.
- Payload: each record is one envelope, framed as `u16be conversation id byte length`, conversation id (UTF-8), then the record plaintext. Records are sent oldest first. Caps: the newest 500 records (`MAX_RECORDS`), then a 4 MiB sealed-byte budget. A frame above one envelope's plaintext bound is skipped. A skipped record does not stop older ones. Older history beyond the caps is not exported, whatever the policy.
- Policy: in the pairing dialog, the authorizing device picks the history the new device keeps (`DevicePairingHistoryPolicy`): 'Last 30 days' (the default), 'All history' or 'Nothing'. Leaving the default adds no step, and the password check on authorize is unchanged. The gateway turns the choice into a history floor once, at authorize time (`DeviceHistoryFloor`): 0 for All history, now minus 30 days for Last 30 days, now for Nothing. The export keeps only records whose `createdAt` is at or after the floor, then applies the caps. Nothing still opens an empty transfer inbox, since every completion carries the secret. Group history is not transferred. More history moves only through a history backup file (see History backup file).
- Floor on the new device: the floor travels inside the encrypted pairing completion as `historyFloor`, which every completion carries. `DevicePairingCodeReader.material` refuses as `invalid` a floor that is not a non-negative safe integer or that lies more than 5 minutes past the new device's clock. Completion stores it per identity (`DeviceHistoryFloorStore`) before the session hydrates or any sync runs. A device that was never paired, or whose stored floor is unreadable, keeps every record. The direct timeline sync, the background read pass and the group inbox sync drop every record dated more than 5 minutes before the floor before any store, display, notification or unread step, and still acknowledge it, so the node does not keep it for this device. The 5 minutes absorb a sender clock that lags the authorizer's. A group commit is applied whatever its date (see Group mailbox key schedule, Send and receive).
- Guarantee: the floor limits what this app copies to the new device and shows there, on an honest client. It is not a cryptographic limit: the new device holds the identity's root key, and the node serves any cursor to a valid reader, so a modified client could read whatever the node still retains. The people in a conversation keep their own copies. The dialog's help text says both.
- Import: the new device hydrates its session, opens its sealed root, and reads the inbox from cursor 0 in pages of 100. It acknowledges each page after storing that page's records. A record is stored only when this identity's sealed root authored it; other records are dropped. Records dedupe on the record id, so a re-run adds nothing. Completion refuses the pairing when no sealed root opens, so the import always runs under one.
- Failures: a publish failure stops the export and is logged without content; the completion still carries the secret and the floor, and the new device imports whatever reached the transfer inbox (nothing when the inbox was never created). An authorize failure after a publish leaves an orphaned transfer inbox that expires with the node's retention. The secret is held in memory only, so a reload before import loses the transfer; the import does not resume after a reload. The export sends one POST per record, sequentially (up to 500); its latency is not measured.
- Specs: `DirectMessageHistoryTransfer.spec.ts` ("exports only the last 30 days under the default policy", "exports every record under All history", "exports no record under Nothing yet still opens the transfer inbox", "exports at most MAX_RECORDS and keeps the newest under the default policy", "exports the newest records within 4 MiB sealed and skips an over-size one under the default policy"); `DevicePairingHistoryPolicy.spec.ts` ("defaults to the last 30 days"); `DeviceHistoryFloor.spec.ts`; `DeviceHistoryFloorStore.spec.ts`; the floor checks in `PigeonDeviceAuthorizationApi.spec.ts` ("refuses a completion whose history floor lies beyond the clock skew"); the backlog in `DirectMessageMailbox.spec.ts` ("drops a record dated before the history floor before storing or showing it, and still acknowledges it", "lets no peer message dated before the history floor mark the conversation unread") and `GroupMailboxInboxSync.spec.ts` ("applies a commit dated before its history floor and drops only the message, so the device stays in the group").
- Import storage full: when the new device cannot store a page (`DirectMessageHistoryStorageError`), the import stops before acknowledging that page, so the transfer inbox keeps it until the node's retention expires it. The import does not resume after a reload, so that history is not imported.

## History backup file

- Export: `DirectMessageMailbox.exportHistory` returns every stored one-to-one record of the identity, oldest first (`DirectMessageHistoryStore.all`). Unlike the pairing export it has no record cap, and it rejects with `DirectMessageHistoryStorageError` when the store cannot be read, so a failure never yields an empty backup. `PigeonHistoryBackup` adds the contact pins and seals the payload with `HistoryBackupFile` after the device unlock is confirmed again; key, format and guarantees are in `docs/local-unlock.md` (History backup).
- Import: `DirectMessageMailbox.importHistory` decodes each record for its conversation and drops anything that is not a version 2 direct record of that conversation. The file is authenticated under the identity root, so own records are tagged again under the current device root (`DirectMessageAuthorship.tag`) and peer records keep their bytes. Records dedupe on the record id, so restoring twice adds nothing. A full store rejects with `DirectMessageHistoryStorageError`; records stored before it stay.
- Not included: group history, mailbox read tokens, MLS and ratchet state, keychain entries.
- Group history gap: `GroupMessageHistoryStore` seals its rows under the device-sealed root, indexes them by tags that hide the conversation, and has no export of an identity's rows. A device signed in with the recovery key therefore starts every group conversation empty, with or without a backup, and shows only what it reads afterwards.
- Simplest way to close it: `GroupMessageHistoryStore.all(session)` reads every row of the identity through the `[identityId, conversation]` index with a range bound to the identity, opens each under the current scope, and rejects when a row does not open, as `DirectMessageHistoryStore.all` does. The payload gains the group records; restore hands them to `GroupMessageHistoryStore.append`, which already dedupes on the record tag and accounts the read markers. MLS verified the records when they arrived; in the file the identity root authenticates them, as it does the peer one-to-one records. No MLS state travels, so a restore brings back past group messages, not membership. The payload change is format version 2, and version 1 is then refused, as any other version is.
