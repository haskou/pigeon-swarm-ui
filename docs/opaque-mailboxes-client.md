# Opaque mailboxes (client)

Client side of haskou/pigeon-swarm-node#289. Module: `src/contexts/mailboxes/`.

## Scope

- 1:1 channel at epoch 0 only.
- The only delivery path for direct 1:1 messages: sent, edited, deleted, reactions, pins, and read receipts. See Direct messages below.
- Direct inboxes can be replicated on up to three availability servers (haskou/pigeon-swarm-node#290). See Availability servers below.
- No rotation announcement and no realtime hint.

## Key schedule

HKDF-SHA256 (`@noble/hashes/hkdf.js`, no salt, 32-byte outputs) over a shared 32-byte secret.

- `info` = label ‖ recipient UTF-8 ‖ u32be(epoch).
- Labels: `pigeon/mailbox/id/v1` (mailbox id), `pigeon/mailbox/post/v1` (post token), `pigeon/mailbox/envelope/v1` (envelope key).
- Read token: derived from the identity root key. See Read token below.
- Node-side capability hashes: SHA-256 hex of the token string (`MailboxCapability.hash`).

Pinned vector: secret `0x01 × 32`, recipient `identity-bob`, epoch 0. The vector asserts the derived mailbox id, post token, and envelope key.

## Read token

- `MailboxReadToken.derive(rootKey, mailboxId)`: HKDF-SHA256 (no salt, 32 bytes) over the device-sealed root (`sessionRootKey(session)`). Info = `pigeon/mailbox/read/v1` ‖ mailbox id. Output is base64url.
- Pinned vector: root key `0x09 × 32`, mailbox id `mailbox-fixture-id`, token `MCkFZKBU05ZYpDeepqRuly-xXmS0bx7Hgq_m0ydOqPI`.
- The token is the same on every device that holds the root key, and it survives re-authorization. A device that lost its storage reads and acknowledges the same inbox without a new PUT. New inboxes persist only the cursor.
- The root key never reaches the node. Pairing seals it to the enrolling device's transport key (`DevicePairingCompletion`).
- The peer holds the conversation secret, which yields the mailbox id, post token, and envelope key, but not the root key. It cannot derive the token, so it cannot read, acknowledge, or delete the inbox.
- The root key also decrypts the identity keychain, which holds the conversation keys. Compromising it already exposes the messages, so the read token adds only the ability to read, acknowledge, or delete the inbox.
- Who can use it: holders of the identity root key, i.e. this identity's own devices. The 1:1 peer holds only the conversation secret, so it cannot read, acknowledge, or delete the inbox.
- What the node sees: create sends only `MailboxCapability.hash(token)`. Each read and acknowledge sends the raw token as `Authorization: Bearer`, and the node checks it against that hash. The node therefore learns the raw token on every read and ack. It can already read and delete the inbox's ciphertext envelopes, and the token adds no new capability beyond that.
- Groups: do not reuse this derivation with a shared conversation or group secret as the input. Every holder of that secret could then read, acknowledge, and delete each member's inbox. Group inboxes need a per-member token. The group key schedule below derives it from the inbox owner's root key.

### Reader set

- Device reader: `MailboxReadToken.deriveDevice(rootKey, mailboxId, deviceCredential)`, same HKDF with info = `pigeon/mailbox/device-read/v1` ‖ u32be(len(mailboxId)) ‖ mailboxId ‖ credential UTF-8. Pinned vector: root key `0x09 × 32`, mailbox `mailbox-fixture-id`, credential `-----BEGIN PUBLIC KEY-----`, `AAAA`, `-----END PUBLIC KEY-----` joined by LF, gives `js4BVkg1uGoEfwYGrPmaTvGh7s8MuZnZhSg1zaYJzDA`.
- A device reads and acknowledges with its device reader. The same token rules as the root apply: the node sees the raw device token on each read and ack.
- The root reader lists, enrols, and removes readers, and it mirrors each acknowledgement, so the root cursor tracks the latest device ack.
- A device enrols its reader when it creates the inbox, and bridges it under the root reader when the inbox already exists (409). After a revoke, the revoking device first registers the new root reader through the replaced root (`previousDeviceSealedRootKey`), best effort. Recovery enrols it again after a re-creation. A refused bridge reads nothing (`reopenInbox` returns outcome `failed` with the sealed readers), and the bridge retries on the next pass.
- Cap: the node's `maxReaders` (`MAILBOX_MAX_READERS`) defaults to 129 on nodes that include haskou/pigeon-swarm-node#437: the root reader plus one reader per device, up to 128 devices. A device enrol past the cap is refused (409) and logged with the fixed inbox-create debug line. Its read then gets 404, recovers, and fails again on enrol with 409. `addReader` maps that 409 to `MailboxReaderLimitError`, and the sync shows the reader-limit notice instead of the generic one. A reader whose device was removed still counts until pruned; the first pass of an app session prunes before the read, so that slot can free in the same pass.
- Pruning: once per app session per mailbox and root, on the first sync pass or the first recipient prewarm open (`openInboxes`), whichever comes first. A device lists the readers and removes any hash that is not the root reader, its own device reader, or a device reader of a credential in the identity's device list, all derived from the device-sealed root. The root reader is never removed. A failed pass logs a fixed debug line and retries on the next sync.
- Mixed versions: a client from before this change reads and acknowledges with the root token only. Its acks do not move the device readers, so envelopes stay until the device readers acknowledge. Update every device.

### Alternatives

- Random token, persisted (previous design): lost with local storage. The node keeps the old inbox, so reads return 404 and the recreate PUT returns 409 until the 14-day retention expires.
- Derived from the conversation secret: rejected. The peer could read, acknowledge, and delete.
- Derived per device (`deviceId`): rejected. The device id changes on re-authorization and on "forget this device", which reproduces the loss.
- Epoch bump on 409 with a fresh mailbox id: rejected. Senders derive from the constant epoch 0, and the rotation announcement is not implemented. Senders would keep appending to the abandoned inbox, so messages would be lost silently. This needs the announcement from the node design doc first.

### Residual risk

- Mixed versions and the reader cap: see Reader set.
- Forget is best effort on readers: forgetting a device removes its device reader through the root token. A failed removal is left to the reader prune that other devices run on sync. The only device of an identity keeps its reader, because its revocation is never sent.
- Revoke rotates the root for the remaining devices (see `device-sealed-secrets-client.md`, Rotation). The revoking device keeps the root it replaced on the in-memory session (`previousDeviceSealedRootKey`). The session update reopens every one-to-one inbox (prewarm). Each open registers the new root reader through the replaced root, then prunes. The prune removes the replaced root's readers and the revoked device's reader, so the revoked device cannot read records written after that point (#311). After that it has no reader, because it cannot fetch the sealed root (401). Other devices bridge through the new root reader. Authorship tags derive from the sealed root, and keychain heads open only under it, so a revoked device cannot forge own-inbox tags or read the post-revoke keychain.
- Revoke residuals (#311):
  - Window: envelope keys derive from the conversation secret, which the revoked device keeps, and the node authorizes each read by the reader set only. Records written between the revoke and an inbox's prune stay readable by the revoked device. Each inbox is pruned on the revoking device's next open, which the session update triggers right away.
  - The replaced root is held in memory only. If the revoking app session ends before an inbox bridges, that inbox keeps only the replaced root's readers. No remaining device can bridge it, so the remaining devices cannot read it while the revoked device still can.
- Forget rotates the root later. The forgetting device revokes itself, so it cannot publish. The first remaining device to unlock finds its own entry behind the head and publishes a fresh root (see `device-sealed-secrets-client.md`, Rotation and Forget). Until then the old root stays registered, and a forgotten device that still holds it keeps read access. A publish before the revoke would not close this window, because the forgetter must be listed as a recipient and would receive the new root too (node `DeviceSealedSecretBundle.assertPublishableBy`). A tighter bound needs a node contract change (`haskou/pigeon-swarm-node#289`).
- Silent readers: a registered reader that stops acknowledging holds every envelope above its cursor until the node's retention expires them (default 14 days). While it is silent the mailbox can fill, and appends return 409. Pruning removes only readers whose device is gone, so a silent device that is still listed keeps its backlog.

## Group mailbox key schedule

Step 2 of node `docs/design/group-mailboxes.md` (haskou/pigeon-swarm-ui#174). Module: `src/contexts/groupMailboxes/`. Group sends and receives do not use it yet; group conversations stay on their legacy endpoints.

- `GroupMailboxKeySchedule` (`infrastructure/crypto/`) derives the material of one member inbox `I(Y,k)`. Inputs and outputs are 32-byte value objects in `domain/value-objects/`, held as unpadded canonical base64url. A rejected value is never echoed in the error.
- HKDF-SHA256, no salt, 32-byte outputs. Input key material is the generation secret `gen_k` (`GroupMailboxGenerationSecret`). `info` = label ‖ slot `s_Y` (`GroupMailboxSlot`, 32 bytes).
- Labels: `pigeon/group-mailbox/id/v1` (`mailboxId`), `pigeon/group-mailbox/post/v1` (`postToken`), `pigeon/group-mailbox/envelope/v1` (`envelopeKey`).
- `envelopeKey` is the AES-256-GCM key of the outer per-copy AEAD of decision D5: random nonce per copy, AAD `mailboxId`. The envelope cipher itself is step 3.
- `readToken` = `MailboxReadToken.derive(rootKey_Y, mailboxId)`: the read token derivation above (`pigeon/mailbox/read/v1` ‖ mailbox id), keyed by the owner's root key (`GroupMailboxOwnerRootKey`). Members know every slot, so they can derive every inbox id, post token, and envelope key of the generation, but not another member's read token.
- None of the outputs depends on an identity or a group id. A member removed before generation `k + 1` has no `gen_{k+1}`, so it cannot derive any inbox of that generation.
- Vectors: `src/test/fixtures/group-mailbox-derivation-vectors.json`, generated with `node:crypto` `hkdfSync`, independent of the module. Each case gives `gen_k`, `s_Y`, and `rootKey_Y` in hex and the expected output for every label. `src/test/contexts/groupMailboxes/infrastructure/crypto/GroupMailboxKeySchedule.spec.ts` checks every case per label (`yarn test:crypto`).

## Creation proof

- Preimage: `[pigeon-mailbox-creation:v1, mailboxId, postTokenHash, readTokenHash, nonce].join(':')`.
- SHA-256 must start with at least `difficultyBits` zero bits. The default is 16 (`MailboxCreationProof.DEFAULT_DIFFICULTY_BITS`). A `PUT` 400 that names `requiredDifficultyBits` raises the requirement; see Creation difficulty and recovery.
- `nonce` is the first passing decimal integer from 0, at most 64 characters.
- Mining runs in a dedicated worker: `mailboxCreationWorker.ts`, driven by `MailboxCreationWorkerClient`, constructed by `createMailboxWorkerClient()`.
- Pinned nonce for the vector: `47805`.
- Shared vectors: `src/test/fixtures/mailbox-creation-proof-vectors.json` is byte-identical to the node's `tests/fixtures/mailbox-creation-proof-vectors.json` (preimage, digest, leading zero bits, mined nonce, rejected cases), checked by `MailboxCreationProof.vectors.spec.ts`.

## Envelopes

- Fixed buckets for the decoded body: 1024, 4096, 16384, 65536 bytes.
- Body = base64url(iv ‖ ciphertext ‖ tag), AES-256-GCM with the envelope key.
- AAD = `${mailboxId}.${envelopeId}`.
- Plaintext framing: u32be(length) ‖ plaintext, zero-padded to the bucket.
- `MailboxEnvelopeCipher.MAX_PLAINTEXT_BYTES` (65504) is the largest plaintext that fits: the largest bucket minus IV, tag, and length prefix.

## HTTP (`PigeonMailboxClient`)

| Action      | Route                                            | Auth                |
| ----------- | ------------------------------------------------ | ------------------- |
| Create      | `PUT /mailboxes/{id}` (201 created, 200 repeat)  | creation proof body |
| Append      | `POST /mailboxes/{id}/envelopes`                 | post token (Bearer) |
| Read        | `GET /mailboxes/{id}/envelopes?after=&limit=`    | read token (Bearer) |
| Acknowledge | `POST /mailboxes/{id}/ack` with `{ upTo }` (204) | read token (Bearer) |
| Readers     | `GET /mailboxes/{id}/readers`                    | root token (Bearer) |
| Enrol       | `POST /mailboxes/{id}/readers` (201 added)       | root token (Bearer) |
| Remove      | `DELETE /mailboxes/{id}/readers/{hash}` (204)    | root token (Bearer) |

- A 404 maps to `MailboxUnavailableError`. A 400 on create that names `requiredDifficultyBits` maps to `MailboxCreationDifficultyError`. A 409 on enrol maps to `MailboxReaderLimitError`. Other 400s, 409s, and 429 propagate as `HttpJsonError`.
- Empty success bodies (PUT 200/201, POST 204) resolve to `undefined` in `HttpJsonClient`.

## Creation difficulty and recovery

- `createInbox` mines at the default 16 bits. If `PUT` returns 400 with `requiredDifficultyBits`, it re-mines once at that value and retries the `PUT`. A second refusal, or a value outside 17 to 24, propagates without re-mining.
- Rate limit: the node caps creations per client address (`MAILBOX_CREATE_RATE_LIMIT_PER_MINUTE`, 30 per 60 s by default). An over-limit create returns 429, which surfaces as `HttpJsonError`. The recipient pass stops at the first 429 and reports incomplete. An inbox whose open failed, rate-limited or not, is not tried again for 60 s (`OPEN_RETRY_MS`), so creation work stays bounded per conversation. Senders never create.
- Recipient `read` and `acknowledge` re-create an evicted mailbox once on 404, with the same id and capability hashes, then retry the operation. A second 404 propagates. Both report `recreated: true` when this happened. The re-creation enrols the device reader again (`createInbox(root)`, then `addReader(device)`).
- A re-created inbox numbers its envelopes from 1 again, because node `nextCursor` starts at 1 for each mailbox. A cursor stored for the old inbox would hide new envelopes. `DirectMessageMailbox.sync` therefore re-reads from 0 when `read` reports `recreated`, and stores cursor 0 when `acknowledge` does.
- Senders (`send`) do not re-create. They lack the read-token hash, so they recover after the recipient's next read or acknowledgement.

## Receive

- Forged or undecryptable envelopes are dropped silently. Nothing about them is logged.
- The returned cursor includes dropped envelopes, so acknowledging up to it removes them.
- Logs never contain decrypted payloads or topics.

## Direct messages

- Scope: one-to-one conversations only. The mailbox is the only delivery and history path for them: the client neither writes nor reads the node's one-to-one message endpoints (see Cutover below). Groups and communities keep their node endpoints and are not described here. Attachments, replies, and stickers travel as opaque encrypted payload inside the sent record.

| Kind                                    | Mailbox record                                    | Status                                                                                     |
| --------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Sent: text, reply, attachments, sticker | `sent` (`replyToMessageId` for replies)           | Carried                                                                                    |
| Edited                                  | `edited` (`targetMessageId`)                      | Carried                                                                                    |
| Deleted                                 | `deleted` (`targetMessageId`)                     | Carried                                                                                    |
| Reaction add / remove                   | `reaction` (`action`, `emoji`, `targetMessageId`) | Carried                                                                                    |
| Read receipts                           | `read` (`targetMessageId`)                        | Own devices only: other devices of this identity clear unread. The peer never receives it. |
| Thread send, edit, delete, reaction     | none                                              | Not carried: thread UI is group-only. One-to-one has no threads to carry.                  |
| Pin and unpin                           | `pin` (`action`, `targetMessageId`)               | Carried. Applied last-writer-wins by `createdAt`; see Pin order.                           |

- Envelope: plaintext is `{kind:'direct-message', version:2, record}`. `record.type` is `sent`, `edited`, `deleted`, `reaction`, `pin`, or `read`. `DirectMessageMailboxRecord.decode` returns null for a wrong kind or version, a wrong conversation, missing or invalid fields, an unknown type, or a bad reaction or pin action.
- v1 `direct-text` envelopes decode to null and are acknowledged, so they do not block the inbox. They are not shown, and nothing is migrated.
- Size: a record whose plaintext exceeds `MailboxEnvelopeCipher.MAX_PLAINTEXT_BYTES` cannot be delivered, so its send rejects. The bound applies to every kind, including a very long text message. Attachment bytes upload as private blobs first; the payload carries only their references, download tokens, expiry, the attachment key, and per-chunk IVs. Each part adds to the payload, so a message with many or large attachments is refused whole and never split across envelopes.
- Send: `directMessages.send` builds the sent record once, with the same encryption, `previousMessageIds`, `replyToMessageId`, and attachment publishing as the former legacy send. It checks that the record fits the envelope and that its conversation key resolves, persists the record in the sealed outbox (see Same-device history), and resolves with the locally projected message. A rejection means nothing was persisted, such as a missing conversation key or an over-size record. Delivery runs in the background with one drain per send, so a send to an absent inbox does not hold back other sends. The peer copy is written first, then the own copy (see Own copy). While the peer's inbox is not open yet (a 404 with no other fault, see 404), the send shows the retry state (`Retrying`) and its peer copy is retried with capped backoff. Any other fault marks the send `failed`, and the user's retry re-queues it. There is no POST to `/conversations/{id}/messages`.
- Edit, delete, reaction, and pin: `directMessages.edit`, `delete`, `reaction`, and `pin` follow the same rule, including the retry window for an absent peer inbox. Each rejects when the peer copy is still not delivered, and the UI shows the error notice. No legacy copy is written in its place.
- Own copy: after the peer copy is delivered, the same record (same id) is appended to this identity's self-inbox (the inbox the peer writes into), tagged with an authorship tag (see Authorship), so the other devices of this identity apply the change. The record is built once. An own-copy failure, including a throw while building it (for example, no root key), is logged as one count-only line. It does not reject the call and is not retried.
- Pin send: the caller passes `createdAt`, taken on the client when the action starts, to `directMessages.pin`. A rejected pin is not in the mailbox, so no other device applies it. The pinned list is not loaded from the node for one-to-one conversations (see Cutover).
- Recipient home: the append goes to `<mailboxHome>/mailboxes/...` when the recipient's identity serves a `mailboxHome` base URL (origin plus optional path prefix, published as the UI's API base) that verifies against the identity signature (`IdentityMailboxHomeVerifier`). Private hosts are rejected; `localhost` is accepted for development. Otherwise, or when the home append throws, the append goes to the connected node. Each fallback logs one count-only debug line (no URL or id). Home calls use an isolated client (`credentials: omit`, `redirect: error`). Reads and acks stay on the connected node, plus the availability servers (see Availability servers). Each send adds one identity lookup. A failed home append can still have stored the envelope, so the fallback can land the same envelope twice; the timeline collapses duplicates by message id. The published hint is last-write-wins across a user's devices.
- Recipient: the active one-to-one conversation is polled about every 5 s (`useDirectMessageMailboxSync`). Each page is decrypted in envelope order into timeline changes (`message`, `edit`, `removed`, `reaction`, `pin`, `read`), applied, then acknowledged. The cursor advances only after a successful ack. These changes are the only source of timeline, unread, and push updates for one-to-one conversations. Legacy realtime message events are ignored for them. Messages collapse by id in `MessageCollection.merge`. A sent or edited change is dropped when its message does not decrypt.
- Replay dedupe: the timeline applies each record id once. A replayed envelope whose record id is already applied adds no change (`DirectMessageTimelineSync`). That set lives in memory per mailbox instance, and restore seeds it from the store, so the store is not consulted for dedupe. Two devices of one identity keep separate sets.
- Own-copy echo: a record whose id this device appended as an own copy is acknowledged and not applied, since this device already shows it. The skip set is keyed by identity and record id and keeps the 512 most recent own copies, in memory only. After a reload the set is empty, so own records appended but not yet read are applied again. The reaction and pin clocks are also empty then, and edits and deletes have no clock, so a replay can override a later local change only when that change never reached the mailbox.
- Reaction order: a mailbox reaction applies only when its `createdAt` is newer than the newest write seen for the same message, author, and emoji. A remove leaves its clock on the message (`reactionClocks`), so a replayed older add cannot reopen the reaction. Local writes apply in arrival order and advance the same clock. The clock is timeline state: it survives a same-id merge but not a reload. After a reload a reaction can reopen only if its remove was never appended to the mailbox, or was acknowledged before an add that was appended later. Mailbox writes use the sender's `createdAt`, so ordering across devices assumes their clocks agree to within the gap between the two actions.
- Pin order: a mailbox `pin` change applies only when its `createdAt` is newer than the last applied change for the same message, so a replayed or out-of-order record cannot undo a newer one. Within one pass, changes apply in order. The clock lives in the sync effect and resets when the conversation or session changes. A pin change updates only the pinned set, never the timeline.
- Pin residual risk: local pin writes do not advance the pin clock. A mailbox pin or unpin applied after a local change to the same message can override that local state. There is no `listPins` load for one-to-one conversations, so nothing from the node corrects it.
- Read receipts: `directMessages.markRead` appends a `read` record (`targetMessageId` is the last delivered message restored) to this identity's own inbox. It replaces the node read-until call for one-to-one conversations. Opening a one-to-one conversation marks it read once its stored history is restored (`useDirectMessageMailboxSync` hands the restored messages to `onHistoryRestored`). It is best effort: it never rejects and never shows an error, and a failure is logged count-only. It runs only for the active one-to-one conversation, once per read mark, with no dedupe; each record is small. The peer's inbox is never written.
- Read receipt apply: the active sync hook and the background pass (`useDirectMessageBackgroundReadSync`) apply a fresh `read` record from this identity's inbox by calling `onConversationRead`, which clears unread for that conversation on this device. The timeline is unchanged. Records from other authors are acknowledged and ignored.
- Freshness: a `read` record applies only when `createdAt` is at most 14 days old and at most 30 s ahead of the local clock, matching the node's `MessageReadProof` limits. Both edges are inclusive. Stale or future-dated records are acknowledged and ignored.
- Trust: a `read` record is authenticated by the conversation key and, when this identity authored it, by its authorship tag (see Authorship). The peer holds the conversation secret, which derives this identity's self-inbox keys, but not the root key. A receipt it writes as this identity is dropped, so it cannot clear this identity's own unread state.
- Authorship: a record whose `authorId` is this identity is applied only when its envelope carries `authorTag`: HKDF-SHA256 (no salt, 32 bytes) over the device-sealed root (`sessionRootKey(session)`, which throws without one), with the label `pigeon/mailbox/own-record/v1` followed by the record's JSON with keys sorted. Only the own-inbox copy is tagged. The peer copy and records from other authors need no tag. The sync path and the background read pass both check the tag, so a record that claims this identity without a valid tag is acknowledged and dropped. A peer that writes into the self-inbox cannot forge or replay a sent, edited, deleted, reaction, pin, or read record as this identity.
- Authorship residual: the sender needs its root key to tag its own copy, which it already holds for reads. An own copy that cannot be tagged (no root key) or exceeds the envelope bound is not written, and the send still resolves on the peer copy.
- Authorship rollout: own copies written before this change carry no tag, so upgraded devices drop them on read. Peer copies are unchanged and the envelope version stays 2, so no version bump is needed. Pre-upgrade own records are not replayed to other devices of this identity.
- Background pass: `useDirectMessageBackgroundReadSync` clears unread on the other one-to-one conversations with `unreadCount > 0`, so a read on another device shows here. Each tick (5 s) visits at most 2 conversations, and each conversation is visited at most once per 30 s. A visit reads at most 4 pages of 50 envelopes. It never acknowledges, writes the shared cursor, or creates an inbox, and it skips an inbox this device has not opened. A clear applies only when the visit reaches the end of the inbox and no sent message from another identity follows the last fresh own read, so an unread message is never hidden. A visit that hits the page limit clears nothing and retries on a later pass. The active conversation is never visited by this pass. On the active sync path, a delayed older `read` can still clear unread for a newer message that arrived after it.
- Pre-create: the recipient inbox of every one-to-one conversation this identity holds a key for is opened (created, device reader enrolled) on session start and whenever the session or the conversation list changes (`useDirectMessageInboxPrewarm`, which calls `DirectMessageMailbox.openInboxes`), not only for the active conversation. Opens run one at a time and skip inboxes already open. A pass that leaves an inbox unopened, or rejects, is retried after 60 s. The sync path opens the active inbox the same way before its first read. Overlapping passes share one creation (`MailboxChannel.createInbox`), so a StrictMode remount sends one PUT. A failure is silent; the read's 404 recovery covers it on the next pass.
- Open marker: `{cursor: 0}` is stored only after the device reader is enrolled. A failed or rate-limited open stores nothing, so the next open retries it instead of skipping it.
- A 404 on append means the node holding the inbox has no inbox for this recipient. A 404 from the recipient's home falls back to the connected node. A 404 there with no other fault seen means the peer has not opened the conversation yet, or its inbox was evicted and not re-created. A send retries its peer copy with capped backoff (250 ms doubling to 4 s) for 30 seconds, then every 60 seconds, for as long as the session lives (see Send). Edit, delete, reaction, and pin retry the peer copy with the same backoff for 30 seconds; if the inbox still does not exist, the call rejects and the user's retry is the only retry after that. A home lookup failure, or a home append that is not a 404, is a fault: a send then marks itself `failed`, and the other writes reject at once with no retry. The own copy gets the same 404 until a device of this identity has opened the conversation's self-inbox. It is then not written and not retried, and the send still completes on the peer copy.
- A failing sync shows one notice unless another error is already shown. The next successful pass clears only that notice.
- The cursor is stored in localStorage under `pigeon.direct-mailbox.<mailboxId>` (scoped per client). Both reader tokens are derived, so clearing storage loses only the cursor. The background pass keeps its own read cursor under `pigeon.direct-mailbox-read.<mailboxId>`, so it never moves the shared cursor.
- A stored cursor is reset to 0 when the inbox is re-created (see Creation difficulty and recovery).
- Gaps: polling only (no realtime hint); no retry beyond the next poll; epoch fixed at 0.
- Multi-device: each device reads and acknowledges with its own device reader, and the node keeps an envelope until every reader has acknowledged it. An ack from one device therefore cannot remove a message another device has not read. The reader set holds at most `maxReaders` readers per inbox (129 by default: the root plus 128 devices), so a device past the cap cannot enrol (see Reader set).

### Cutover: node 1:1 path retired

The mailbox is the only delivery and history path for one-to-one conversations. No shim, fallback, feature flag, or history migration remains. The client neither writes to nor reads the node's one-to-one message endpoints. Groups and communities keep their node endpoints; this cutover does not change them.

- Removed for one-to-one:
  - Send, edit, delete, reactions (add and remove), pin, unpin, and the pin list (`listPins`).
  - `read-until` (`conversations.markReadUntil`). Its replacement is the own-inbox `read` record.
  - `loadAround` and `loadThread` for one-to-one conversations. The reply-target fetch shows an error, and threads are group-only.
  - Realtime message events for one-to-one conversation ids.
  - The copy model: the additive copy written after each legacy one-to-one write, its separate delivery outcome, its side-effect helper, and the copy notice that reported a failed copy. The own copy now follows the peer copy and shares its record id; a failed own copy is only logged (see Own copy).
  - The message POST as a carrier of 1:1 attachments. They reach the peer only through mailbox records. The attachment downloader's legacy methods stay, because group and community history use them.
  - The timeline message list (`messages.load`, on open and on older pages) and latest-message recovery (`PigeonConversationRepository`) for one-to-one conversations. `useConversationTimeline` builds a one-to-one timeline only from the mailbox restore and sync, and keeps it on a resume. Latest-message recovery runs only for groups.

- Accepted losses (decided; not backfilled):
  - One-to-one history is never loaded from the node. Mailbox envelopes are deleted on full acknowledgement, so a 1:1 message that is in neither the local history store nor the projection cache is gone after a reload. The local store is described in Same-device history.
  - No backfill for restored devices. A device paired from an authorized device receives that device's stored one-to-one history (see Pairing history export), within its caps. A post-cutover own copy reaches only devices that read the self-inbox within the node's 14-day retention. Messages written to the node's one-to-one endpoints before the cutover are no longer shown. Design: `docs/design/own-copy-and-history-backfill.md`.
  - A 1:1 send to a peer whose inbox is not open yet is retried until its peer copy lands, with no give-up while the session lives. It survives a reload and sign-out through the sealed outbox and resumes on unlock (see Same-device history). Sends in the same conversation no longer queue behind a pending one, so concurrent sends share a predecessor and appear as siblings. A forget that runs while a peer copy is in flight can still leave that copy on the peer's inbox, and the attachment blobs of a forgotten send remain until the node's retention removes them. A send whose peer copy lands but whose `peerDelivered` flag is not saved before a stop or reload is appended again on resume; the recipient's timeline collapses messages by id.
  - Edit, delete, reaction, and pin are rejected when the peer copy is not delivered, and the UI shows the error notice.
  - Read receipts never block and never show errors. A failed receipt is not retried; the next read mark sends a new one.
  - Pinned state after a reload comes only from pin records still in the mailbox and from the local cache.
  - v1 `direct-text` messages are not shown. Own copies written before the authorship change are dropped on read (see Authorship rollout).

- Open risks (caveats; not addressed by this cutover):
  - Oversized records have no mailbox copy: a record above `MailboxEnvelopeCipher.MAX_PLAINTEXT_BYTES` is refused and its send rejects. Attachment-heavy messages need a split or a larger bound first.
  - Attachment references carry `expiresAt`. How node blob lifetime compares with the 14-day mailbox retention was not checked.
  - Retention: an envelope not acknowledged by every reader expires after the node's retention (14 days by default). A device that stays away longer loses those messages.
  - Silent or evicted readers can fill an inbox. Appends then return 409, and every one-to-one send to that inbox fails until the reader is pruned or the envelopes expire.
  - Reader cap: 128 devices per identity. An extra device has no read path for the inbox.
  - Own copies double the envelopes in this identity's self-inbox. A full self-inbox refuses both the own copy and the peer's sends into it, so a stuck own device blocks the peer too.
  - A failed own copy is not retried, so the other devices of this identity miss that change.

## Availability servers

Client side of haskou/pigeon-swarm-node#290: a direct inbox is kept on several nodes, so a message still lands and reads while the recipient's home is down.

- Config: `VITE_MAILBOX_AVAILABILITY_SERVERS` is a comma-separated list of API bases, set per deployment (`MailboxAvailabilityServers.pick`). Each entry resolves against the page origin as `VITE_API_SERVER_URL` does and is kept only when it is a publishable mailbox base (`MailboxHomeBase`: no private hosts; `localhost` for development). Repeats and the connected node are skipped, and at most 3 are kept. Unset means no availability servers, and the client behaves as before. Each server is reached through an isolated client (`credentials: omit`, `redirect: error`).
- Open: the sync pass and `openInboxes` open the own inbox on the connected node first, then on each picked server, with the same creation proof, device reader, and retry window. Each server keeps its own cursor and open marker under `pigeon.direct-mailbox.<base>:<mailboxId>` (`DirectMessageMailboxStore(base)`), so the servers never share a cursor.
- Announcement: after each sync pass, even a failed one, the recipient tells the peer which picked servers hold its inbox open, when that list changed since its last announcement. The announcement is one envelope in the peer's inbox, sealed by the conversation key like any record: plaintext `{kind:'direct-mailbox-servers', version:1, authorId, conversationId, createdAt, servers}` (`DirectMessageAvailabilityAnnouncement`). The last list sent is stored under `pigeon.direct-mailbox-announced.<mailboxId>`. A failed announcement is retried after 60 s (`OPEN_RETRY_MS`) and logs one count-only line.
- Trust: the receiver keeps an announcement only when it decodes, names this conversation, and its `authorId` is the conversation peer; `servers` must be at most 3 distinct canonical publishable bases. Anything else is acknowledged and ignored. Lists apply last-writer-wins by `createdAt`: an announcement not newer than the stored one is ignored. The list is stored under `pigeon.direct-mailbox-servers.<peerMailboxId>`. The announcement is not a timeline change.
- Fan-out: every append to the peer's inbox (sends, edits, deletes, reactions, pins, announcements) goes to the primary route (verified home, else the connected node; see Recipient home) and to each server the peer announced, in parallel, with one envelope id (`RecipientMailboxRouter.send`). Own copies go to this device's picked servers the same way. The call resolves when the primary or any server stores the envelope; it rejects with the primary error only when every target fails. Each failed server append logs one count-only line.
- Read and dedupe: the sync pass reads the connected node, then each picked server, through the same decrypt, apply, and ack path. One record arrives once per server, and the timeline applies each record id once (see Replay dedupe). A server is read only once its inbox is open there. A failed server read logs one count-only line and does not stop the other reads; a failed connected-node read still rejects the pass after the servers were read. A page a server's read cannot store is not acknowledged on that server (see Storage full), and the pass rejects with `DirectMessageHistoryStorageError` in place of any connected-node error, so the sync notice shows.
- Release: `releaseDeviceReaders` removes this device's reader on the connected node and on every picked server.

### Availability residual risks

- Only the timeline sync and own-inbox appends use the servers. The realtime hint target, the background read pass (`syncReads`), and the pairing history transfer stay on the connected node.
- No reader prune runs on the servers; a removed device's reader there lapses only with the node's retention.
- A peer chooses which public hosts, up to 3, receive appends to its inbox. Those hosts see the same opaque envelopes and mailbox ids as the home does.
- There is no per-user picker: the servers are deployment config only.
- A server that is down is retried on every sync pass and every append; only its failures are logged.

## Same-device history

- Store: each stored record of a one-to-one conversation (sent, edited, deleted, reaction, pin; read receipts are never stored) is kept in IndexedDB (`pigeon-direct-history`, scoped by `scopeClientStorageKey`), sealed with AES-256-GCM. The key is HKDF-SHA256 over the device-sealed root, with info `pigeon-direct-history:v1:<identityId>`. A per-identity canary detects a root rotation, such as after a device revoke or forget: a mismatch, or a missing canary while rows exist, wipes that identity's rows. The wipe is remembered in memory and reported once by `DirectMessageMailbox.checkHistoryDropped(session)`; a deliberate `forgetHistory` is not reported.
- Outbox: a one-to-one send not yet delivered to both inboxes is one row in IndexedDB (`pigeon-direct-outbox`, scoped by `scopeClientStorageKey`). The row holds the built record and the peer id, sealed with AES-256-GCM under a key derived by HKDF-SHA256 over the device-sealed root, with info `pigeon-direct-outbox:v1:<identityId>`. A per-identity canary detects a root change and wipes that identity's rows, as in the history store. The row is saved before the first delivery attempt and records `peerDelivered` once the peer copy lands, so a resume repeats only the own copy. Unlock loads every row and drains the pending ones (`DirectMessageMailbox.resumeOutbox`); sign-out stops the in-memory drain and keeps the rows (`stopOutbox`). A `failed` row stays until the user retries it or the device is forgotten. Without a device-sealed root nothing is stored. Forget wipes the identity's rows (`cancelOutbox`) after the device revocation succeeds, also when the unlock removal fails. A failed revocation keeps them.
- Write: the sync pass appends each page's records before it acknowledges the page, own copies included. Entries dedupe on the record id the sender mints once per action, so a replayed envelope adds nothing and each reaction add, remove, or re-add keeps its own row. The id is stored in clear for the index; no digest of the content is kept.
- Storage full: a failed write, such as an exhausted browser quota, rejects with `DirectMessageHistoryStorageError`, which carries no content. The pass still shows the page but does not acknowledge it, so the node keeps its envelopes and the cursor stays. The sync notice says the messages could not be saved on this device and stay on the server for up to 14 days. Each poll reads the same page again, retries the write, and acknowledges it once the write succeeds; the replayed records are already applied, so nothing shows twice. While the write fails, later pages are not read, and an envelope left unstored past the node's retention (14 days by default) is lost. Without a device-sealed root nothing is stored and the page is acknowledged, as before.
- Restore: the first sync pass per session and conversation first replays the stored records in stored order (`DirectMessageMailbox.restore`), then runs the normal pass. The replayed records count as applied, so the pass skips them. Logout keeps the store, so re-login shows the history again.
- Deletion and replay: a removed message stays removed. If the sender re-posts the envelope of a message the timeline already applied, its record id is in the applied set (seeded by restore after a reload), so the replay adds no change and the message does not return. No spec covers this case yet; it follows from the applied-set rule above.
- Forget: `forgetHistory(identityId)` wipes the identity's rows once the device revocation succeeds, including when the unlock removal fails and for a confirmed only-device forget. A failed revocation keeps them.
- Revoked from another device: the next sign-in on this device detects the removal (`DeviceRemovedError`, see `local-unlock.md`, "Revoked device on unlock"). Before the sign-in screen says so, `eraseRemovedDevice` wipes the identity's outbox rows (`cancelOutbox`), history rows and canary (`forgetHistory`), and pending device-sealed recovery records (`discardDeviceSealedRecovery`). Each step runs even when another fails. If a step rejects, the screen says the messages could not be erased, and "Erase local copy and start over" retries the wipe before it removes the vault record. As on forget, the history and outbox stores log an IndexedDB failure without content and do not reject, so today only a refused localStorage removal reaches that message. The wipe needs that sign-in: a revoked device that stays signed in keeps its rows until it signs in again, because nothing checks the device's authorization during a session. Drafts (`pigeon:conversationDrafts:<identityId>`, sealed under the root) are not wiped by this path.
- Device storage: after unlock the workspace asks the browser once, without a prompt of its own, to keep the site's data (`navigator.storage.persist()`, only when not already persisted; `DeviceStorage.protect`). It then shows one dismissible notice: that the stored history was cleared (`checkHistoryDropped`), or else that space is low (`DeviceStorage.estimate`: under 50 MiB free or at least 90% of the quota used). Nothing is shown otherwise. Profile, Security, "Storage on this device" shows usage and quota, whether the data is persisted, and what is kept on this device, on the server (up to 14 days), and with other people. When the browser cleared the whole site, the vault is gone too, and sign-in says so (`auth.localDeviceMissing`).
- Not covered: envelopes acknowledged before this change were never stored, and the node has deleted them, so they are not restored.

## Pairing history export

- Trigger: before it authorizes a new device, the authorizer publishes its stored one-to-one history into a transfer inbox (`DirectMessageHistoryTransfer.publish`). Without a device-sealed root nothing is written or read, so nothing is exported. The secret is 32 random bytes per pairing. It travels inside the encrypted pairing completion as `historyTransferSecret`, which every completion carries: `DevicePairingCompletion.open` refuses material without it as `invalid`.
- Node view: the transfer inbox is keyed from the secret (`MailboxKeySchedule.derive(secret, identityId, 0)`), and its read token is `MailboxReadToken.derive(secret, mailboxId)`. The node sees the mailbox id and the hashes of the post and read tokens, never record plaintext or the secret.
- Payload: each record is one envelope, framed as `u16be conversation id byte length`, conversation id (UTF-8), then the record plaintext. Records are sent oldest first. Caps: the newest 500 records (`MAX_RECORDS`), then a 4 MiB sealed-byte budget. A frame above one envelope's plaintext bound is skipped. A skipped record does not stop older ones. Older history beyond the caps is not exported.
- Import: the new device hydrates its session, opens its sealed root, and reads the inbox from cursor 0 in pages of 100. It acknowledges each page after storing that page's records. A record is stored only when this identity's sealed root authored it; other records are dropped. Records dedupe on the record id, so a re-run adds nothing. Completion refuses the pairing when no sealed root opens, so the import always runs under one.
- Failures: a publish failure stops the export and is logged without content; the completion still carries the secret, and the new device imports whatever reached the transfer inbox (nothing when the inbox was never created). An authorize failure after a publish leaves an orphaned transfer inbox that expires with the node's retention. The secret is held in memory only, so a reload before import loses the transfer; the import does not resume after a reload. The export sends one POST per record, sequentially (up to 500); its latency is not measured.
- Import storage full: when the new device cannot store a page (`DirectMessageHistoryStorageError`), the import stops before acknowledging that page, so the transfer inbox keeps it until the node's retention expires it. The import does not resume after a reload, so that history is not imported.
